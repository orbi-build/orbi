# OpenCode provider

OpenCode is a **Pi-native** provider. This page records the behavior measured with
Pi **0.85.1 on 2026-09-07**; OpenCode's catalog, plans, and limits can change.
It is linked from the provider Epic [#305](https://github.com/orbi-build/orbi/issues/305).

## What was actually verified

The installed Pi CLI reports the provider credential variable
`OPENCODE_API_KEY` and the built-in provider id `opencode`. The installed catalog
contains the model ids listed below. `timeout 30 pi auth check --provider opencode --json --no-refresh` on the
verification account returned:

```json
{"status":"not_ready","provider":"opencode","reason":"credentials_not_configured"}
```

Therefore this checkout does **not** claim a successful OpenCode request, quota
consumption, or Orbi PR. A real delivery must be recorded only after an account
with OpenCode credentials runs it; do not copy the z.ai or Gemini delivery
numbers to this provider.

## Authentication

1. Obtain an OpenCode API key from the OpenCode account/plan that owns the
   desired quota. Keep it outside Git and outside Issue, journal, and PR text.
2. For Pi's built-in login, start interactive Pi, enter `/login`, select
   OpenCode, and choose the API-key option; Pi stores the credential in its
   private auth file. Alternatively, export the key for a manual check, or put
   it in the private environment file loaded by the Orbi systemd unit:

   ```bash
   pi
   # enter: /login, then select OpenCode and API key
   export OPENCODE_API_KEY='...'
   timeout 30 pi auth check --provider opencode --json
   ```

3. Pi 0.85.1 also documents `pi auth check`, `print-api-key`, and
   `print-bearer-token`. The observed OpenCode credential contract is an API key;
   no OpenCode-specific OAuth flow is required. If a future Pi version changes
   this, repeat the commands above and update this page before documenting it.

## Catalog and Orbi configuration

Pi owns this catalog, so **do not create or copy a `pi_providers.json` entry** for
OpenCode. Defining a second OpenAI-compatible endpoint would pin stale model
metadata and is not the native path. Set only the selectors in `orbi.toml`:

```toml
pi_provider = "opencode"
pi_model = "glm-5.3-flash"
```

models and `https://opencode.ai/zen/v1` for the Google/OpenAI-compatible models.

## Quota, limits, reset, and errors

No OpenCode account or plan was authenticated during this measurement. Thus
this page intentionally records **no numeric quota, rate limit, reset time, or
plan promise**. Verify those values in the OpenCode account's current plan
before budgeting a run. An unavailable/expired key is observable in Pi as
`credentials_not_configured` from `pi auth check`; an upstream quota or rate
failure must be captured from the actual Pi/Orbi journal response, including its
HTTP status and provider message. Never infer reset behavior from a model name.

For a completed real delivery, append dated evidence here or in the linked
Issue: account/plan boundary (not the secret), journal `provider` and `model`,
`run_id`, PR URL, and elapsed time. This checkout has no such evidence.

## Real Orbi delivery checklist

After authentication, run one small Issue in the user's own repository and
record the journal lines `provider=opencode model=<id>`, the stable Orbi
`run_id`, the PR URL, and elapsed seconds. A delivery is not proven by
`pi auth check` alone. Do not put the API key in any artifact.

## Minimal fallback

Keep the Orbi runner unchanged. For z.ai, copy the existing `z-ai.json` template
to `.orbi/pi-providers.json` and put `ZAI_API_KEY` in `.orbi/env`; the complete
selector change is:

```diff
+pi_providers = ".orbi/pi-providers.json"
-pi_provider = "opencode"
-pi_model = "glm-5.3-flash"
+pi_provider = "z-ai"
+pi_model = "glm-5.3-flash"
```

For a local Qwen setup, use the existing `local-qwen.json` template and select
its exact advertised model id; do not reuse the OpenCode model id. See [provider
templates](/providers) and [Getting started](/getting-started).
