# OpenCode Zen provider

This page is the Orbi setup for **OpenCode Zen**, OpenCode's curated model
service, and is part of the [provider documentation Epic (#305)](https://github.com/orbi-build/orbi/issues/305). It is separate from the OpenCode terminal application's project
configuration: Orbi runs Pi, not OpenCode.

> **Evidence boundary — 2026-09-07.** The checks below used the installed Pi
> CLI **0.85.1**. `pi auth check --provider opencode --json --no-refresh`
> recognized `opencode` and returned `credentials_not_configured` (exit 1).
> No OpenCode account or API key was available in this environment, so a real
> model request, quota consumption, and an Orbi Issue-to-PR run were **not
> tested**. Do not read this page as a claim that an account has capacity.

## Authentication

OpenCode's official flow is API-key authentication, not an OAuth login from
Orbi:

1. Open [OpenCode authentication](https://opencode.ai/auth), sign in, add
   billing details, and create/copy an OpenCode Zen API key.
2. Put the key in the environment used by Orbi. The recommended project-local
   method is a mode-600 `.orbi/env` file (it is not committed):

   ```bash
   mkdir -p .orbi
   printf '%s\n' 'OPENCODE_API_KEY=replace-with-your-key' > .orbi/env
   chmod 600 .orbi/env
   ```

3. Check the credential before dispatching an Issue:

   ```bash
   pi auth check --provider opencode
   ```

   A configured key should no longer report `credentials_not_configured`.
   This check does not spend quota. For an optional real smoke request, use
   the exact model selected below:

   ```bash
   pi --provider opencode --model glm-5.3-flash --print 'reply with: ok'
   ```

Pi also has an interactive `/login` flow for API-key providers. It is optional
here: `/login` stores the key in Pi's `~/.pi/agent/auth.json`, whereas the
`.orbi/env` method makes the credential explicit to the Orbi systemd unit.
There is no need to run an OpenCode OAuth flow or to put an OpenCode credential
in OpenCode's `~/.local/share/opencode/auth.json` when Orbi is using Pi.

## Pi and Orbi configuration

Pi 0.85.1 has a native provider with this contract:

- provider: `opencode`
- API key: `OPENCODE_API_KEY`
- service endpoint: Pi's built-in OpenCode Zen endpoint
- supported APIs: native Anthropic Messages, Google Generative AI, OpenAI
  Completions, and OpenAI Responses adapters, selected by the catalog entry

Therefore **do not create `pi_providers.json` for OpenCode** and do not copy an
OpenCode entry into a second provider file. A `pi_providers` file is for
custom/provider definitions; duplicating Pi's native entry can become stale
and is unnecessary.

Set only the selectors in `orbi.toml`:

```toml
pi_provider = "opencode"
pi_model = "glm-5.3-flash"
```

Leave `pi_providers` unset. Orbi's installed unit loads `.orbi/env`; for a
manual run, export the variable first because a shell does not load that file
automatically:

```bash
set -a; . .orbi/env; set +a
orbi --help >/dev/null
```

Run `orbi setup`/the normal config validation before claiming the provider is
ready. The selected provider and exact model must be present in Pi's current
catalog.

## Credits, limits, reset, and failures

According to the [official Zen documentation](https://opencode.ai/docs/zen/),
Zen is pay-as-you-go and charges per request. It supports account credits,
auto-reload (below $5, reload $20 by default, configurable or disable-able),
and monthly limits for a workspace and individual team members. The official
page does not promise a universal free allowance or a fixed reset time; limits
and model availability are account/workspace/plan dependent. Several models
marked `Free` are explicitly described as available for a limited time.

This run did not possess an account, so the following are deliberately **not
measured here**: remaining balance, request rate limits, reset timing, an HTTP
status/body for exhausted credits, and whether any listed model is enabled for
a particular plan. A failed credential, disabled model, exhausted credit, or
upstream rate limit is a failed Pi model request; Orbi must leave the run
failed rather than silently retrying or claiming the Issue reached a PR.
Inspect the redacted Pi/Orbi error, then verify the key, balance, workspace
limit, model access, and current catalog in OpenCode.

## Minimal fallback

Keep the Issue and runner unchanged. Change only the provider selection (and
secret if the replacement needs one). For the repository's existing local
Qwen template:

```diff
 pi_provider = "opencode"
-pi_model = "glm-5.3-flash"
+pi_providers = ".orbi/pi-providers.json"
+pi_provider = "local-qwen"
+pi_model = "Qwen3.8-27B"
```

Copy `templates/pi-providers/local-qwen.json` to
`.orbi/pi-providers.json`, and ensure the local OpenAI-compatible server is
running. For z.ai, copy `templates/pi-providers/z-ai.json`, use
`ZAI_API_KEY` in `.orbi/env`, and change only the three selector values to
`pi_provider = "z-ai"` and `pi_model = "glm-5.3-flash"`. These fallbacks have
their own availability and quota requirements; they are not guaranteed
capacity.
