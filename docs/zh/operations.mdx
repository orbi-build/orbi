# 运维

正常运行完全自动：timer 触发 tick，tick 最多做一件事，进度自己发布到
journal 和 GitHub。正常路径永远不需要 status 命令、轮询或督工——下面的
命令只用于首次验证、排查和恢复。

## Timers

timer 模板 `systemd/orbi@.timer` 部署为**两个实例**：
`orbi@1.timer` 和 `orbi@2.timer`。每个实例每 5 分钟触发
一次，全天 24 小时（`OnCalendar=*-*-* *:00/5`、`AccuracySec=30s`、
`Persistent=false`——错过的 tick 被丢弃，从不排队），并各自启动自己的
service 实例（`orbi@1.timer` → `orbi@1.service`，
`orbi@2.timer` → `orbi@2.service`），所以可以同时运行
两个独立的 Runner 实例。每个 tick 的 service 实例：

1. **先同步 engine source**（`ExecStartPre`，在 Runner 进程外）。两个
   步骤，都包在一个短生命周期的 `flock`（共享状态目录下的
   `base-sync.lock`，Python 侧同步取同一把锁）里；两个实例可能在同一
   tick 运行 `ExecStartPre`，并且自 Issue #171 起，所有更新共享
   remote-tracking ref 的 fetch 都走同一把锁：Runner 侧的
   `freeze_base` / `verify_pr` / `merge_gate` / `confirm_merged` fetch
   统一经 `fetch_base_ref`（先取锁 → fetch → 释放，锁或 fetch 出错即
   fail fast），implement/review 两个 prompt 指示 Pi 用
   `flock <BASE_SYNC_LOCK> git fetch origin <base_branch>` 执行 base
   新鲜度 fetch（锁路径从配置的 `repo_dir` 渲染进两个 prompt）。两个
   并发 Runner（或 Runner 与 Pi 会话）因此不再争抢共享 ref（不会出现
   `cannot lock ref ... is at <X> but expected <Y>` 失败）。两个步骤
   作用的 checkout 都是**部署 home**——`{{ORBI_REPO_DIR}}` 占位符在
   安装时渲染的是 `deploy_home` 路径（缺省 `repo_dir`），所以外部单仓
   库模式（Issue #330）下同步、锁和 CLI 自愈全部作用于 orbi 源码
   checkout，绝不作用于交付 checkout（用户仓库 X）。

   - **步骤 1 —— CLI 自愈**（Issue #248）：探测已安装的 console
     script（`orbi --version` 当且仅当包可导入时成功），探测失败时在
     同一把 `base-sync.lock` flock 下执行精确的 editable 强制重装
     （`uv tool install --force --reinstall --editable --python
     /usr/bin/python3 <repo_dir>`）。这是 console script 连
     `import orbi` 都失败时唯一能动手的地方——#248 现场：#168 的
     src 布局迁移让已安装的 editable finder 过期，而 #158 的 Runner
     内刷新（在 Runner **内部**运行）根本不可达。它排在同步**之前**，
     因为同步子命令需要可用的 CLI。健康的 CLI 退出 0，其余什么都不做
     （不逐 tick 重装）；重装失败则 preflight 失败、service 不启动
     （fail fast，无回退）。
   - **步骤 2 —— engine source 同步**（Issue #535）：`orbi
     sync-engine-source` 把部署 home 带到配置的 engine source 更新
     通道。通道是 deploy home `orbi.toml` 里的 host/deploy-only 配置
     键 **`engine_source_track`**（仓库的 `.github/orbi.toml` 永远
     不允许携带它；模式与失败行见下文
     [engine source 更新通道](#engine-source-更新通道)）。缺省 `main`
     通道保持 #535 之前的精确行为：`git fetch --no-auto-maintenance
     origin main && git merge --ff-only origin/main`——fast-forward 到
     `origin/main`。每次 fetch 都带 `--no-auto-maintenance`，避免 Git
     子进程脱离 preflight 和共享锁的生命周期。checkout 不干净、fetch
     失败、tag/SHA/branch 缺失、无法 fast-forward、或任何无法对照解析
     结果验证的状态都会让 preflight 失败：service 不启动，原因写入
     systemd journal（fail closed）。每种失败各写一条结构化、可操作的
     行（`deploy_home_dirty files=... fix=...`、
     `engine_source_unresolved reason=...`、
     `engine_source_not_fast_forwardable ...`）；成功时同步写一条结构化
     `engine_source_synced engine_source_track=... resolved=... head=...`
     行。通道不是缺省的 `main`（`branch:`/`release`/`tag:`/`sha:`）时，
     Runner 也会跳过 merge 之后对部署 checkout 的 fast-forward：通道
     拥有该 checkout，下一个 tick 的步骤 2 会重新施加它。

   正在运行的长任务从不被热更新或杀掉——一个 service 实例 active 时
   systemd 忽略对**该实例**的后续 start 请求，下一次真正启动取到通道
   跟踪的代码。
2. **运行一个 tick**：恢复一个已打开的 PR（review/fix/merge），或领取
   一个 `ai-ready` Issue，然后退出。在任何 slot 或领取之前，tick 还
   运行启动前 **git transport 检查**（Issue #114、#580）：部署 checkout
   的 `origin` remote 必须匹配配置的传输方式（orbi.toml
   `git_transport`：`ssh`——默认，`git@github.com:owner/repo.git`；或
   `https`——`https://github.com/<repo>.git`，凭据走 `gh` credential
   helper），且对第一个配置 source repo 的 `git ls-remote
   <expected-url>` 退出 0（传输可达且已认证）。
   传输损坏记录结构化 `transport_check_failed ... reason=...` 行并让
   启动失败——不取 slot、不领取、不改标签，**没有回退**（GitHub
   API 操作永远留在 `gh` token 上）。同样在任何 slot 或领取之前，tick
   运行 **runner 执行代码新鲜度门禁**（Issue #525）：证明本进程执行
   的代码与配置的 engine source 通道一致（Issue #535：
   `engine_source_track`，缺省 `origin/main`——绝不是交付目标的
   `base_branch`）——见下文
   [Runner 执行代码新鲜度与防线分层](#runner-执行代码新鲜度与防线分层)。

```bash
systemctl --user list-timers 'orbi@*.timer'
systemctl --user status 'orbi@*.service'
```

## engine source 更新通道

Issue #535 用一条显式通道取代了硬编码的"永远跟随 `origin/main`"。
host/deploy-only 配置键 `engine_source_track` 位于 deploy home 的
`orbi.toml`——仓库的 `.github/orbi.toml` 里绝不允许出现（runner 在那里
按 host-only 键拒绝它）：

| `engine_source_track` | 下一次启动时部署 home 跟随的源 |
| --- | --- |
| 缺省 / `main` | `origin/main`，fast-forward——#535 之前 dogfood 的精确行为 |
| `branch:<name>` | `origin/<name>`，fast-forward（会 checkout 该分支） |
| `release`（别名 `stable`） | 最新的正式 semver tag（`vX.Y.Z`；`vX.Y.Z-rc.1` 之类的 pre-release 和非 semver tag 被排除），detached checkout |
| `tag:<name>` | 精确锁定该 tag（annotated tag 解引用到其 commit），detached checkout |
| `sha:<40-hex>` | 精确锁定该 commit，detached checkout |

- **`release` 与 `tag:`——跟随与锁定**：`release`（别名 `stable`）跟随
  最新已发布版本，新 tag 发布后自动跟进——只在发版时变化（`main` 每次
  提交都变）。`tag:<name>` 锁死一个精确版本，不改值就永不移动——版本
  变更永远是一次有意操作；要求部署保持可复现时用它锁定，回滚就是把
  上一个 tag 改回去。
- **安装与更新**：`install.sh` 新安装复制 `.orbi.example.toml`，其中
  携带 `engine_source_track = "release"`——新部署跟随最新 release，而
  不是 main 的中间态。Orbi 自有 dogfood 部署显式固定 `main` 通道。
  通道值在下一次 service 启动时生效（ExecStartPre 同步施加它）；没有
  守护进程，也不会重启正在运行的 Runner。
- **回滚**就是把 track 改回旧的 `tag:`/`sha:` 值（或
  `release`/`main`）——git 状态是唯一的存储，没有别的状态要清理。
- **fail closed**（service 不启动，每行都带 `fix=`）：
  - `deploy_home_dirty files=... fix=...`——tracked 本地编辑会阻塞
    同步；用 `git -C <deploy_home> stash && systemctl --user start
    orbi@1.service` 保存后重试（之后 `stash pop`），或用
    `git -C <deploy_home> checkout -- .` 丢弃。
  - `engine_source_unresolved reason=tag_not_found|tag_conflict|sha_not_found|branch_ref_missing|no_official_release_tag`——
    通道无法解析（先 fetch、核对名字，或发布 release tag）。
  - `engine_source_not_fast_forwardable`——分支在本地已分叉（部署
    home 永远不应携带本地 commit）。
  - `engine_source_unverified`——HEAD 无法证明等于解析出的 commit。
- **成功证据**：每次启动一条结构化
  `engine_source_synced engine_source_track=... resolved=... head=...`
  journal 行。
- **doctor** 只读上报通道：`engine_source: track=... resolved=...
  head=...`（通道本地无法解析时输出带同样 reason 的 `FAILED` 行）。
- GitHub 拒绝按未广播的 SHA fetch（`not our ref`），所以 `sha:` 通道
  一次性 fetch 全部已广播 ref，再在本地验证 commit；只能从未合并的
  PR 分支可达的 SHA 因此 fail closed——请锁定 tag/release。
- 交付目标不受影响：`base_branch` 继续管辖任务 worktree 与交付 PR
  （engine/delivery 的语义隔离是 Issue #543 的主题）。

## Runner 执行代码新鲜度与防线分层

2026-09-07 事故：editable install 解析到了一个旧 issue 的 worktree，而
`ExecStartPre` preflight 一直把部署 home 同步得很好——Runner 执行着旧
代码，每笔交付看起来却都是新的（base_sha 新鲜、引擎陈旧），一个早已
修复的 bug 在生产复现。"checkout 被同步了"和"进程执行的是那个
checkout"是两个不同的事实，所以 tick 在任何 slot 或领取之前必须证明
第二件（Issue #525）：

- **editable 安装**（官方部署形态）：门禁解析**运行中进程**的 import
  源（`orbi.__file__` → `src/orbi` 包目录，绝不是 WorkingDirectory），
  用 `git rev-parse --show-toplevel` 定位其所在 checkout，并要求该
  checkout 的 `HEAD` 等于配置的 engine source 通道的期望 commit：
  `main`/`branch:` 通道取已 fetch 的 `refs/remotes/origin/<branch>`
  头，`release`/`tag:` 通道取解析出的 release/tag commit，`sha:` 通道
  取精确 SHA。worktree 与部署 home 共享 refs，所以事故场景（install
  绑到旧 worktree）在这里被拒绝。
- **非 editable 安装**（uv tool / PyPI 拷贝）：安装的发行版本
  （`importlib.metadata`）不得旧于通道对应的 release tag——跟踪分支
  ref 上可达的最新 tag，或锁定的 `release`/`tag:` 版本本身。`sha:`
  锁无法映射到版本，按不可验证 fail closed。相等或更新即通过。
- 全部是**本地 git 读**（`rev-parse` / `describe` / `tag --list`）：
  已 fetch refs/tags 的新鲜度由 `ExecStartPre` 同步供给，checkout 一
  致时零网络请求。任何**无法证明新鲜**的状态（origin ref 缺失、无
  release tag、import 源无法定位）都以同样方式失败并带 `reason=`
  字段——绝不静默放行。
- 落后或无法证明时输出结构化
  `runner_source_stale install=... source=... engine_source_track=...
  head=... origin_main=... allowed=false fix=...` 行并 fail fast：不取
  slot、不领取、不改标签。`fix` 是对 deploy home 的精确 editable 强制
  重装命令。`allow_stale_runner: true`（getting-started）把同一行降级
  为告警，供离线/受限网络机器使用——绝不跳过检查。

**自举边界（为什么需要分层）。** runner 内的自检只能保护**包含**自检
的 runner 版本：旧到没有自检的 runner 无法自检，而 in-runner 的
`unit_drift` 对比恰恰运行在可能被冻结的进程里。因此分层是严格的，
从外到内：

1. **`ExecStartPre` preflight**（CLI probe 自愈 + engine source 同步，
   Issue #535）是最外层防线：由 systemd 在 Runner 进程存在**之前**
   执行——probe 步骤是包裹已安装 console script 的纯 shell，探测失败
   就从 checkout 重装它，因此连 `import orbi` 都失败的 CLI 也会先在
   这里被修复。保持已安装 unit 跟上模板（`install-units` 与启动前检查
   的 `unit_drift` 自愈），这道 preflight 就永远存在。
2. **runner 执行代码新鲜度门禁**（本节，Issue #525）是 in-runner
   不变量：从它发布的版本起，代码陈旧的 runner 拒绝领取任务，而不是
   无声地失败。

## 暂停、迁移或移除部署

部署不只有 editable `uv` tool：用户级 systemd unit 会继续从配置的
`deploy_home` 启动 timer。迁移 checkout 时，必须**先停止旧部署，再安装
新部署**。`deploy_home` 应放在持久目录（例如 home 目录下），不要放在
`/tmp` 或其他重启后可能消失的临时目录。

### 暂停部署

只想暂停 Orbi、保留所有文件时，先停用并停止 setup 可能启用的每个 timer
实例：

```bash
systemctl --user disable --now orbi@1.timer
# max_concurrency = 2 时也执行：
systemctl --user disable --now orbi@2.timer
```

如果改动前已有 service 在运行，先检查它：

```bash
systemctl --user status 'orbi@*.service'
```

上面的命令不会删除 checkout、任务 worktree、`orbi.toml` 或
`<repo_dir>/.orbi/` 状态。要恢复同一套部署，保留已安装的 unit，重新启用
需要的 timer（或执行 `orbi setup --config <deploy_home>/orbi.toml`）。

### 迁移到新的 deploy home

1. 在旧部署上执行上面的暂停命令。必须先做这一步，再删除或改名旧目录；
   否则启用中的 timer 会继续唤醒并持续记录失败日志。
2. 确认新的 `deploy_home` 是持久目录，在那里 clone 或移动 Orbi checkout，
   并更新其中的 `orbi.toml`。保留 `repo_dir` 指向交付 checkout；改变
   `deploy_home` 不应移动或删除该 checkout、它的 worktree 或 `.orbi/` 状态。
3. 在新的 deploy home 安装 unit 并启用所需数量的 timer：

   ```bash
   cd <new-deploy-home>
   orbi setup --config orbi.toml
   ```

   `max_concurrency = 1` 会启用 `orbi@1.timer`；`max_concurrency = 2` 还会
   启用 `orbi@2.timer`。用下面的命令确认结果：
   `systemctl --user list-timers 'orbi@*.timer'`。
4. 如果新部署使用与旧部署相同的 `unit_name`，setup 已经替换了 unit
   文件；**不要**再删除它们，否则也会删除新部署的 unit。如果明确改用了
   新的 `unit_name`，只有在新部署验证正常后才能删除旧 unit。先按上面的
   步骤停用旧 timer，再执行 `systemctl --user daemon-reload`。除非已经
   单独确认数据可以丢弃，否则不要把 repo、worktree 或 `.orbi/` 目录作为
   unit 清理的一部分删除。

如果配置了 `unit_name`，把下面命令中的 `orbi@1/2` 换成对应名称（例如
`orbi-website@1/2`）。

### 完全移除本机上的 Orbi

先暂停部署。默认 unit 名称下，只有在两个可能的 timer 都停用后，才删除已
安装的模板：

```bash
systemctl --user disable --now orbi@1.timer
# max_concurrency = 2 时也执行：
systemctl --user disable --now orbi@2.timer
rm ~/.config/systemd/user/orbi@.service ~/.config/systemd/user/orbi@.timer
systemctl --user daemon-reload
```

删除前检查路径，确认只删除用户 systemd unit 文件。这些清理命令**不会**删除
Orbi checkout、配置的 `repo_dir`、任务 worktree、`orbi.toml` 或
`<repo_dir>/.orbi/`；这些内容只有在确认不再需要后才另行删除。如果本机以后
完全不再使用 Orbi CLI，再把卸载 editable tool 作为单独的最后一步（可选）：

```bash
uv tool uninstall orbi
```

`uv tool uninstall orbi` 不属于暂停或迁移步骤，也不会清理 systemd unit 或
仓库状态。没有 `orbi uninstall` 或 `orbi teardown` 命令。

## Unit 模板变更后（Issue #131、#142）

unit 模板（`systemd/orbi@.service` 和 `systemd/orbi@.timer`）
是部署配置，不是普通代码——但模板变更合并后**不需要任何人工步骤**。模板
位于部署 home（`deploy_home`，缺省 `repo_dir`——Issue #330），漂移检查
对比的是**这些**模板与已安装 unit。下一次 timer 触发时 `ExecStartPre`
同步部署 home checkout，启动前
`unit_drift` 检查自动自愈：用同一个幂等安装（把两个模板复制到用户
unit 目录、daemon-reload、按 `max_concurrency` enable 或 disable timer
实例——从不启动、停止或重启运行中的 Runner）、再用同一个哈希检查复核，tick 继续，每个 unit
记录一行结构化 `unit_drift auto_synced`（before/after sha256、部署
commit）。不再出现“每 5 分钟重复同一个 `unit_drift` 错误直到人工
介入”的循环（#131/#140 实例：每次启动都因 `unit_drift` 失败，直到
人工运行同步命令）。同一个安装还会**一次性迁移** #149 之前的非模板
unit（`orbi.service` / `orbi.timer`）：停掉旧 timer（停
的是 timer，绝不停 service）并删除旧文件，旧单实例调度不会再拉起旧
service。

`orbi install-units --config orbi.toml` 保留为手工入口
（首次 setup、需要立即同步时）。自愈后仍漂移（安装步骤失败、模板
缺失、复核前 unit 再次漂移）时，启动仍然 fail fast（结构化
`unit_drift` 行、非零退出、不取 slot、不领取 Issue）：哈希校验和
哨兵边界不变。

## 日志（journal）

journal 是本地记录。一个 run 的每行都以 run id 前缀 `[<run_id>]` 开头，
一条 grep 还原完整时间线：

```bash
journalctl --user -u orbi@1.service -u orbi@2.service -f
journalctl --user -u orbi@1.service -u orbi@2.service | grep e07383c2
```

你会看到的稳定 `key=value` 行：

- `run_start` / `run_end` — 开始时的完整现场（branch、worktree、
  session 文件），结束时的结果（PR URL、commit）；
- `activity` / `heartbeat` / `model_wait` / `resumed` — session 运行
  期间的实时 Pi 活动（phase、最近动作、elapsed、idle）。首个响应到达
  前 `phase` 是启动子阶段：`session_pending`（Pi 已启动但还没创建
  session 文件）和 `request_pending`（session 已存在、首个响应还没
  到）；首个响应到达后按原规则用工具 phase（`test`、`pr`、`bash`…）；
- `process_spawned` / `provider_config_loaded` / `session_created` /
  `first_request_started` / `first_response_received` — 启动阶段行
  （Issue #176）：每个阶段一行、按顺序，每行带 issue、role、Pi 实际
  选择的 provider/model（session 的 `model_change` 记录出现前为
  `-`）、距 spawn 的 elapsed（`process_spawned` 另带 pid）。
  `provider_config_loaded` 由 Runner 在 spawn 前记录（provider 文件已
  加载并物化；未配置时用 Pi 自己的 agent dir）；其余四行由 streamer
  在 session JSONL 跨过每个里程碑时记录（session 记录、第一条 user
  消息——首个请求发出——第一条 assistant 消息——首个响应到达）。卡在
  `starting` 的 run 只靠这些行加 progress 评论的 `phase` 就能定位到
  启动阶段；只记录标识符——从不记录 key、prompt 或模型输出；
- `startup_failed` — run 在首个响应之前失败时的一行（Issue #176）：
  说明启动卡在哪（`session_created=true|false`、
  `first_request=true|false`）加可区分的 `reason=`——
  `session_not_created`（Pi 退出前没创建 session 文件）、
  `no_first_request`（session 存在但没有首个请求）、
  `provider_rate_limited`（provider 429——Issue #321）、
  `auth_failure` / `network_timeout`（从 Pi 的 stderr 分类——只记类别、
  从不记文本）、`pi_exit_<N>`（提前退出码）、`timeout`（run deadline）、
  `first_response_timeout`（冻结的 `model_wait` 在响应前被杀——挂死的
  首个请求）、`model_wait_swallowed` 和 `idle_recovery_stale`
  （既有 kill 路径）。既有的 `run_failed` 现场行和抛出的失败不变——
  `startup_failed` 是额外的可观测性，不是新的失败路径；
- `resume_continue` — 恢复的 run 继续中断的工作（Issue #219）时的一次
  INFO：worktree 的 run state 文件（`.orbi/run-state.json`）
  验证了同一个 run（issue 编号 + 仓库名——仓库改名后 slug 变了也能
  找到旧 worktree），且 worktree 带有未提交改动或之前的 session；
  行带 worktree、`changed_files`（未提交路径）、`reused_runs`
  （之前的 session 文件数）和 `previous_session`（session id 或 `-`）；
  新 session 在 prompt 里收到 resume context（继续既有工作——从不
  重做、从不丢弃）。同一个 run 无法验证（state 文件缺失或损坏）时
  行是 `resume_continue_failed`：fail fast，Issue 进入 `ai-blocked`
  并带原因——从不静默 fresh 重做；
- `pi_idle` — 超过 300 秒（`PI_IDLE_WARN_SECONDS=300`）没有
  model/session 活动且模型不期望回复时的一次 WARNING；活跃的慢模型
  （`model_wait`）从不告警；
- `model_wait_swallowed` — 冻结的 `model_wait` 被 `/slots` 探针确认
  吞请求（Issue #233）时的一次 WARNING + 杀掉 Pi 会话：
  `model_wait_probe_url` 端点报告**所有** slot 持续
  `model_wait_probe_seconds` 宽限（默认 60 秒）都空闲
  （`is_processing=false`）——请求被上游接受但从未被调度进 slot，
  模型进程活着、连接 ESTABLISHED，但没有东西在生成（#231 现场）；
  行带 issue、role、idle 秒数、探针宽限、`action=kill_pi`、session、
  run id、`upstream_alive=true|false` 和
  `reason=swallowed_model_request`。它快速触发（远早于
  `model_wait_dead_seconds`），吞请求约 1 分钟就能恢复而不是约 30
  分钟。探针是纯旁路（Issue #79）：探测失败视为无证据（无此行，
  `model_wait_dead` 兜底仍生效），有 slot 在处理会重置空闲窗口（慢
  模型不是吞请求）；未设置 `model_wait_probe_url` 时禁用；
- `model_wait_dead` — 冻结的 `model_wait`（最近一条事件是 tool
  result，无新事件）超过配置的 `model_wait_dead_seconds`（默认
  1800 秒，`PI_MODEL_WAIT_DEAD_SECONDS`，Issue #228）时的一次 WARNING
  + 杀掉 Pi 会话：模型请求挂死——连接还活着、模型服务进程还活着都
  只是行上的证据（`upstream_alive=true|false`），不是豁免（进程活着
  ≠ 在回话，Issue #218）；行带 issue、role、idle 秒数、实际配置的
  阈值、`action=kill_pi`、session、run id 和 `reason=hung_model_request`。
  阈值度量的是**完整** session 事件之间的静默（Pi 不向 JSONL 写
  token 级进度），不是 token 级模型进度——持续追加事件的慢生成永不
  触发（慢本地模型，如 ~17 tokens/s 的 Qwen 27B、llama-server 请求
  超时 1200 秒，在默认配置下可以存活超过 10 分钟的完整消息）；
- `pi_idle_wait` — idle-stall 恢复的宽限行（Issue #181）：仍在
  deadline 内的 coreutils `timeout <seconds> ...` 包裹是合法的长命令，
  不是 hang。Runner 每次 stall 记一条 `pi_idle_wait` 行（run id、
  pid、cmdline、deadline），并在 progress 评论里报告 `recovery=wait`；
  先过一个完整 idle 窗口的宽限再升级，之后每个窗口重新评估；
- `pi_retry_429` — provider 限流重试每次一次 WARNING（Issue #321）：
  Pi 非零退出且 stderr 带 429 标记（`429` / `quota` /
  `RESOURCE_EXHAUSTED` / `retry in`）——这是瞬时限流，不是任务失败。
  同一个 Pi 会话在同一个 run 里退避后重新拉起：优先用 429 响应自带的
  重试提示（`retry in Ns` / `retryDelay: Ns`），没有就默认递增
  （30 秒翻倍），两者都封顶 5 分钟。行带 run id、issue、role、
  `attempt`、`next_retry_in`、重试上限 `limit`（5）和 session；
  等待期间持有 slot（本 run 等待时不认领新 Issue）。`attempt` 计数是
  RUN 的，不是进程的（Issue #698）：它持久化在工作树的 `.orbi/`
  运行目录里，跨 runner 重启持续累加，上限才能真正触达终态。5 次退避
  重试仍以 429 退出（连续 6 次 429 退出）之后，交付在每个阶段都是
  终态——`ai-blocked`，绝不走可恢复续跑——失败评论带累计次数与修复
  动作（配额窗口恢复后把 Issue 重新标为 `ai-ready`；终态会清掉持久化
  计数，重排的尝试从全新预算开始），`run_failed` 现场标记
  `reason=provider_rate_limited`。长期额度耗尽不在这里处理
  （#313 的轮换语义接管）；
- `run_failed` — 完整现场加原因（`pi_exit_N`、`timeout_...s`，或
  `model_wait_swallowed_idle_...s`——`/slots` 探针确认所有 slot 持续
  空闲（Issue #233）Runner 快速杀掉 Pi，`model_wait_dead_stale_...s`
  ——冻结的 `model_wait` 超过配置的 `model_wait_dead_seconds`（默认
  1800 秒，Issue #228）判定模型请求挂死，Runner 杀掉 Pi，
  `idle_recovery_stale_...s`——session 连续 `PI_IDLE_RECOVERY_CYCLES`
  （默认 3）个 idle 窗口保持空闲、Runner 杀掉 Pi，或
  `provider_rate_limited`——provider 429 在本轮全部退避重试后仍失败
  （Issue #321））。

idle 告警和模型请求挂死 kill 是日志/健康阈值——它们不是每 5 分钟
调度，也不是业务任务 timeout。

## CLI（`orbi`）

正式入口是安装后的 `orbi` console script，以 **editable**
`uv tool` 安装——为什么必须 editable（`ExecStartPre` checkout 同步、
免重装的源码变更、打包输入刷新）定义在[快速开始](/zh/getting-started)
第 2 步。`orbi doctor` 报告一致性（`cli_source: clean` 或
`cli_source: DRIFT` + 结构化 `cli_source_drift` 行：实际导入路径、
期望 deploy_home、精确的 editable 重装命令），`orbi setup` 校验或
重装。期望来源是**部署 home**（`deploy_home`，缺省 `repo_dir`——Issue
#330）：外部单仓库模式下 `cli_source` clean 表示 editable 安装从 orbi
checkout 导入，即使交付 checkout 是外部仓库 X。checkout 根目录**没有** `orbi.py`（与 package 同名的 flat
文件会遮蔽已安装 package）；直接执行入口 `python3 -m orbi.cli`
运行与 console script 完全相同的代码，保留为开发/兼容路径。

```bash
# 在配置的 source repo 创建 Issue 并加 ai-ready 标签
orbi add "task title" --body "task body" --config orbi.toml
orbi add "task title" --repo OWNER/BACKLOG-REPO --config orbi.toml

# 只读队列视图：当前（ai-in-progress）任务带实时 Pi 活动、下一个 ready
# Issue、每个 source repo 的最近结果（ai-pr-opened / ai-fix-needed /
# ai-merged / ai-blocked）
orbi status --config orbi.toml

# 只读部署/健康报告：repo commit、unit drift、CLI 源码（cli_source:
# clean / DRIFT + 结构化 cli_source_drift 行）、git transport（配置的
# origin URL、protocol、配置的 git_transport 的期望 URL、可达性探测——传输失败报告为
# `transport: FAILED ...`，不抛出）、timer/service 实例状态、slots、
# Pi session、当前 Issue、最近 journal
orbi doctor --config orbi.toml

# 一次性、幂等初始化（新机器/新仓库）：gh auth + 仓库权限、平台 labels、
# systemd user units、checkout 检查（含 git transport：处于相反传输的
# `origin` 迁移为配置的 `git_transport` 的 URL（HTTPS->SSH 或
# SSH->HTTPS；人工授权的迁移路径；Runner 本身从不改写 remote），并探测
# 传输连通性（fail fast，没有回退））
orbi setup --config orbi.toml

# 打印当前 run 的 Pi session JSONL 路径（没有 session 时 fail fast）
orbi session --config orbi.toml
orbi session --follow --config orbi.toml   # tail -f
orbi session --pretty --config orbi.toml   # 一行摘要
```

所有命令通过 `--config` 或 `ORBI_CONFIG` 环境变量接收配置
（默认 `orbi.toml`）。`status` 和 `session` 是调试附件——
journal 和 GitHub 仍是正常可观测路径。

## Worktree 与 base 新鲜度

每次领取先 fetch 并冻结 `origin/<base_branch>`，任务 worktree 和按
Issue 稳定命名的 feature branch 都从那个精确 SHA 创建——绝不来自主
工作区当前 HEAD。分支在重试之间保持稳定；worktree、Pi session 目录和
run 产物带 run id，所以重试的 Issue 得到新的独立 run，旧现场保留。
`.worktrees/` 已 gitignore。

任务 worktree 继承部署 checkout 的单一 `origin` remote，所以 git
transport 只配置一次、所有 worktree 继承（Issue #114——双通道边界与
启动前检查：见上文 Timers 第 2 条；凭据：[安全](/zh/security)）。

agent 在提交的交付处停止；PR 前的 base 新鲜度是 Runner 的确定性收口
（Issue #186，`deliver_pr`）：Runner 在 base-sync 锁下重新 fetch
`origin/<base_branch>`，用普通 `git merge` 吸收前进的 base（冲突时
中止，PR 在 agent 的 head 上打开——已有的审查会话在会话内吸收
base），然后推送 task branch 并创建 PR。

## 故障恢复

| 状态 | 发生了什么 | 怎么办 |
|---|---|---|
| `ai-blocked` | 只用于 AI 无法安全判断或修复的外部前置条件（Issue #50：现场无法恢复、base 分支变更、审查超轮、PR 未合并被关闭）——comment 写明为什么不能自动恢复 | 读 Issue 评论（现场 + 原因）和 journal。修环境或修任务，然后把同一 PR 路径重新标为 `ai-fix-needed`（同一 run 继续），或移除标签重新派发为全新 `ai-ready`（新 run）。它从不自动恢复。 |
| `ai-fix-needed` | PR head 尚不可合并（review finding、base 冲突），或已有 run/PR 的可恢复失败（Issue #50：Pi 执行失败、验证失败、未推送本地 commit、worktree 缺失） | 什么都不用做——下一 tick 在同一 run_id、branch、worktree、PR 上启动下一个审查会话，会话内吸收最新 base。 |
| 被杀后残留的 `ai-in-progress` | Runner 在任务中途被 SIGKILL | 下一 tick 的重启扫描接回（仅当没有其他 Runner 活着时）：同一 run id、同一 worktree、同一条进度评论——不新建 run。 |

run 产物（plan、test log、session JSONL）留在任务 worktree 作为本地
记录；GitHub 承载交付记录。

## Run 卡在 `session_pending`：首个模型请求发出前挂死（Issue #311）

**症状。** Runner 拉起 Pi 后，会话始终不创建 session 文件、也不发出
首个模型请求。Run 停在 `session_pending`，15 分钟后被 idle-stall 恢复
杀掉（`idle_recovery_stale_15m`），Issue 落到 `ai-blocked`——每次失败
白烧 15 分钟 slot，且需人工重新派活。在线 provider 会中招（z.ai 与
google gemini 均复现）；127.0.0.1 的本地模型不受影响。特征：session
JSONL 路径为空，而 pi 进程还活着。

**30 秒取证**（对卡死的 run）：

```bash
PID=<journal `process_spawned` 行里的 pid，或 `pgrep -f pi`>

# 1. 活着但空闲：state S、~0% CPU、epoll 空转
ps -o pid,stat,%cpu,wchan:32 -p "$PID"

# 2. 没有任何到模型 API 的 TCP 连接——请求从未发出
ss -tnp | grep "$PID"                    # 空

# 3. 唯一的 socket 是 D-Bus
ls -l /proc/"$PID"/fd | grep socket      # unix socket -> /run/user/1000/bus

# 4. session 文件从未创建
ls -la <任务 worktree>/.pi-session/      # 空
```

**根因。** per-run agent dir 物化机制（Issue #303）让 Runner 的 Pi 加载
`~/.pi/agent/settings.json` `packages` 里声明的用户级插件。
`pi-mcp-adapter` 插件启动时初始化 `@napi-rs/keyring` → Secret Service
（`org.freedesktop.secrets` / `kwalletd6`）D-Bus 调用；在 systemd
`--user` 服务上下文该调用偶发永不返回，node 在发出任何模型请求前就挂
在 `poll_schedule_timeout`。

**修复。** 从 `~/.pi/agent/settings.json` `packages` 移除
`pi-mcp-adapter`（已验证：同一 run resume 后 15 秒内 `session_created`
+ `first_response`）。永久修复是 Issue #249——orbi 自声明 extensions
（`[[pi_extensions]]`）并以 `--no-extensions` 启动 Pi，用户级插件从此
无法泄漏进无人值守会话。上游：向 pi-mcp-adapter 报 bug（无 MCP server
配置时不应硬初始化 keyring，或改惰性初始化）。

## 并发

`max_concurrency`（默认 1）限定本机并发交付数。slot 是
`<repo_dir>/.orbi/slots/slot-N` 上的排他 `flock(2)` 锁，在任何
领取之前取得，整个交付生命周期（implement → review → merge）持有；
进程无论如何退出，内核都会释放它。拿不到 slot 的 Runner 记录
`capacity_full` 后退出，不领取 Issue。`max_concurrency = 2` 时两个 timer
实例可能在同一 tick 启动两个 Runner 实例；为 `1` 时只启用 `@1.timer`。
它们竞争同一组 slot——容量和启用的 timer 数都由 `max_concurrency` 决定
（固定模板只允许 `1` 或 `2`）。
