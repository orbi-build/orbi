使用者——人、脚本或托管产品——可以依赖的一切都列在本页；未列出的都属于私有实现，可能随时变化。

[Constitution](https://github.com/orbi-build/orbi/blob/main/CONSTITUTION.md) 承载架构不变量，本页承载接口规范：公开接口清单，以及状态观察与进度摘要的精确格式。本页是唯一的公开接口清单入口。

## 契约原则

- 使用者只能依赖在本页正式记录的接口。私有实现不是契约。
- 变更已记录的契约，必须在同一个 PR 里更新文档并写 release note；即使所有测试通过，静默变更也是缺陷。
- 接口清单是接口规范，不是架构不变量。新增、修改或删除一行属于正常的接口演进：更新本页与 release notes 即可，不是宪法修正。
- 改变架构不变量的改动，仍然像其他任何条款一样，走 Constitution 第 7 条的修正流程。

## 状态观察契约

本节规定 `orbi status` 与 `orbi status --follow` 的观察行为。它用有归属的完整记录取代 mtime 猜测。

### 范围与选择

status 运行默认打印每个已配置 source repository 的快照。`--follow` 改变观察时长，不改变范围。`--repo OWNER/REPO` 选择一个已配置仓库，`--issue N` 选择其中的一个 Issue。只配置一个 source repository 时允许只选 Issue；配置多个时必须配合 `--repo`。非法选择器在任何读取之前就被拒绝。视图保留容量、slots、队列与最近结果，并在多个交付并发运行时显示每一个活跃交付。

### 归属与成员

观察键是已配置仓库加 Issue 号。仓库绝不从全局 slug 反推，Issue 号精确匹配：Issue 42 不能匹配 Issue 420。

只有在目录名匹配该仓库既有的完整命名约定 `.worktrees/orbi-<owner>-<repo>-issue-<N>-<run_id>` 时，该 worktree 才是候选。worktree 名归属 run；完整 JSONL session 记录归属 session；完整事件时间戳归属活动时间。目录或文件 mtime、文件名顺序、随机 run id 都不能证明当前正在执行。

示例：已配置仓库 `acme/shop`、Issue 42 匹配前缀 `.worktrees/orbi-acme-shop-issue-42-`；`.worktrees/orbi-acme-shop-issue-42-86b57234` 的合法八位十六进制后缀给出 run `86b57234`。完整 JSONL 头部 `{"type":"session","id":"sess-1","timestamp":"2026-10-15T06:20:00Z"}` 给出 session `sess-1`；活动时间来自对应的完整 activity 记录。

活动行的成员来自最近一次完整成功的 GitHub 范围读取，并沿用既有 Orbi 状态语义。本地 worktree 只把这些 Issue 的观察挂上去：文件发现不能把旧 Issue 加回活跃集合，且首次成功范围读取之前不猜测任何活动成员。某个 Issue 离开该集合时，会直接读取它，并在下一次成功的 GitHub 刷新之前展示其确认的退出结果；随后移除它的活动行。如果交付 A 完成而交付 B 继续，A 保留的目录不能让 A 重新变为活跃。显式的 `--issue` follow 会保留该 Issue 直到 Ctrl-C，可以展示有归属、带时间的历史观察，但不声称执行仍在进行。

快照读取每个候选 session 最近一次完整且有归属的观察。follow 在进程内存里保留每文件偏移，复用完整的 JSONL 解析，并在同一范围内发现新的 worktree 与 session。不完整或无法归属的记录意味着“没有可读活动”，绝不是“空闲”。如果多个保留记录无法证明哪个 run 还活着，就展示带归属的观察与时间并明确标注不确定性；绝不静默选一个。不展示任何原始消息。

Label、PR 与 check 结果、以及确认的完成状态始终是权威。只有当匹配的既有 journal 记录明确关联同一个 run 与同一个 Issue 时，才展示 Runner 阶段；否则阶段未知（null）。绝不从工具名推断阶段，也绝不假定某个实例日志文件的最后一行是全局最新。写入方从自己已绑定的 Runner 上下文取得阶段。

### 读取周期

本地发现与增量读取以 0.5 秒为周期，设计目标是在健康本地条件下约一秒内展示一个完整本地事件。初始扫描建立最新观察；后续周期只读新的完整记录。这是记录级观察，不是 token 流，也不是端到端保证。

GitHub 状态有独立周期：启动时立即读取，每次完整读取后等待 15 秒。单 Issue 范围只读该 Issue；仓库与全仓库范围通过既有读取命令与分页解析器完整分页 open Issues，然后套用既有 Orbi 状态语义——没有任意的 1/50/200 总数上限。新的 GitHub 任务在这个周期上发现，不一定在 0.5 秒内出现。先前活跃的任务从集合中消失时，会先对它做一次直接状态读取，再展示确认结果、手动等待或移除。Issue follow 保留其 Issue 直到 Ctrl-C。

GitHub 读取绝不阻塞本地事件展示：前台命令内一次有界后台读取即可。状态读取周期绝不重叠。保留最近一次成功的视图；既有有界读取重试都失败后，点名受影响的仓库与 Issue 并以非零码退出。Ctrl-C 干净结束，不留下孤儿读取任务。没有 daemon、没有持久游标或历史、也没有刷新设置。

Linux 与 macOS 的 journal 入口与 JSONL 来源就是既有那些（评审基线：`systemd_deploy.py:328-349`、`launchd_deploy.py:80-86,253-274`、`scheduler.py:175-185`、`pi_activity.py:58-90,284-325`、`pi_process.py:1103-1124,1245-1285`）。macOS 日志没有全局顺序保证。

### 路径策略

read 或 edit 的活动目标必须规范化为 worktree 内、相对于仓库的路径：worktree 内的绝对路径会以对应的相对路径发布，因此任何绝对路径都不会出现在任何一种表示中；越界、位于外部或无法归属的目标变为 null。排除 `RUNNER_RUNTIME_EXCLUDES` 路径（单一定义在 `pi_activity.py`，由 `pi_session.py` 为 worktree exclude 固定与 dirty-worktree 门禁导入）——`.orbi/`、`.worktrees/`、`.pi-session/`、`.pi/`，以及根目录的 `plan.md`、`test.log`、`verify.md`——以及 `.git` 元数据。带有 HTML 注释字符（`<` 或 `>`）的目标同样变为 null：隐藏块在序列化时转义这些字符，而正文逐字发布同一个值，因此可能开启或提前终止注释的值会在渲染之前就从两种表示中被丢弃。既有配置解析出的凭据与 provider 文件（`<deploy_home>/.orbi/env` 与 host-only 的 `pi_providers` 文件）位于任务 worktree 之外，因此同一条包含规则就会拒绝它们；没有额外设置，也没有启发式文件名字典。正文与隐藏块共用这项检查。它发布已知边界内的路径；不发布文件内容，也不承诺检测未知文件里的任意机密。

## 进度摘要契约

### 进度块

每个 run 保留它唯一既有的 progress comment。它的正式起始是既有 run 标记紧跟 `orbi:progress:v1` 块，结束时也一样：

```html
<!-- orbi:run=86b57234 -->
<!-- orbi:progress:v1 {"step":"review","reported_at":"2026-10-15T06:20:20Z","activity":{"at":"2026-10-15T06:20:18Z","kind":"read","target":"src/login.ts"}} -->
```

版本只属于标记。payload 要求 `step`、`reported_at` 与 `activity`。

- `step` 是已记录的阶段或 null。只有 Runner 确认的动作才设置 `starting`、`implement`、`review`、`checks`、`merge` 与 `release`；review 包含评审者的修复。`checks` 出现在两处：PR 打开之后直到评审 session 开始，以及合并门禁的检查。它不代表评审已通过，也不代表仍有进程在运行。未映射的任务类型用 null。
- `reported_at` 是报告生成时间，UTC ISO-8601 字符串，不能为 null。heartbeat 可以推进 `reported_at` 而不推进 `activity.at`。
- 没有任何已知活动类型可发布时，`activity` 为 null。

### activity 形状

`activity` 不为 null 时，`at`、`kind`、`target` 三个键都必需、绝不省略：`at` 是活动的 UTC 时间戳或未知时的 null，`kind` 是 `read`、`edit`、`command`、`analysis` 之一，`target` 是安全的仓库相对路径或 null。

```json
{"at":"2026-10-15T06:20:18Z","kind":"read","target":"src/login.ts"}
```

```json
{"at":"2026-10-15T06:20:18Z","kind":"command","target":null}
```

```json
{"at":"2026-10-15T06:20:18Z","kind":"read","target":null}
```

`command` 与 `analysis` 保留 kind 与活动时间，`target: null`；它们绝不暴露参数或文本。不安全的 `read` 或 `edit` 目标也变为 null，同时保留已知的 kind 与时间。没有已知活动是 `"activity": null`，绝不是空对象。

### 报告选择

从完整分页里，先按既有可信发布者与 run 范围评论规则，找出最近更新的正式 run 记录。该候选不需要 progress block；被引用或围栏包裹的标记不是正式记录。然后选出属于同一个 run 的、最近更新的 progress comment，并把它归为 `missing`、`unsupported`、`invalid` 或 `available`。started 或 milestone 记录不会丢弃同一 run 已经存在的 progress comment。

如果该 run 没有 progress comment 或没有可读摘要，就不用另一个 run 的摘要当作它的当前报告。较旧内容只能作为明确标注的历史出现，并带有自己的 run 与时间。选择的是最近报告的 run 归属，不是最近一次 start，也不是活着的进程。终态与手动 GitHub 事实保持优先。

### 内容与安全规则

从结构化事件生成一个安全值，正文与块都由它渲染。read 或 edit 目标校验为仓库相对路径；绝对或越界路径、凭据位置、内部运行时目录与 HTML 注释字符都被拒绝，因此没有任何目标能终止隐藏块或在可读正文里伪造注释。序列化同样会被转义，即使某个值带着这些字符，块也不会被提前终止。已拼装好的命令字符串绝不二次清洗。prompt、分析文本、源码、输出与机密在两种表示里都绝不发布，结束时也一样；恢复与失败记录保留它们自己既有的契约。

### 读者与发布边界

读者按既有作者规则校验可信发布者，校验精确的无引号正式前缀、受支持的版本与完整分页。候选与 run 的选择（包括没有块的记录）遵循上文“报告选择”。PR、check 与终态事实不重复写进 payload。没有当前 run 指针、没有新的 run 排序、没有第二条评论流、没有恢复存储。发布始终是尽力而为：它失败不会改 label、不会阻塞、不会跳过、也不会让交付、评审或合并失败。这是展示契约，不是任务状态。

### 协议示例

下面这些评论正文是供读者集成使用的协议 fixture：run 归属与时间戳都来自记录本身，写入方绝不发布伪造或损坏的形态。消费者用它们验证自己的选择与展示逻辑；本页只记录这些形态。

```html
<!-- trusted author, formal prefix, summary available: run marker followed by the versioned block -->
<!-- orbi:run=86b57234 -->
<!-- orbi:progress:v1 {"step":"review","reported_at":"2026-10-15T06:20:20Z","activity":{"at":"2026-10-15T06:20:18Z","kind":"read","target":"src/login.ts"}} -->

<!-- forged: the marker quoted inside prose or a fence is NOT a formal record -->
> <!-- orbi:run=86b57234 -->

<!-- a newer run without details: marker only, classification missing -->
<!-- orbi:run=5c1d0a77 -->

<!-- unknown version: unsupported; the rest of the view still renders -->
<!-- orbi:progress:v9 {"step":"review"} -->

<!-- corrupt payload: invalid; the rest of the view still renders -->
<!-- orbi:progress:v1 {"step": -->

<!-- late old-run update: still attributed to run 86b57234 and its own times -->
<!-- orbi:run=86b57234 -->
<!-- orbi:progress:v1 {"step":"merge","reported_at":"2026-10-15T07:44:00Z","activity":null} -->
```

终态或手动状态这类 GitHub 事实——Issue 已关闭或已合并，或处于已确认的手动等待——优先于任何已发布或本地的摘要；被引用、被围栏包裹或版本未知的 marker 永远不会被选作报告当前的 run。

## 评论类型与机器元数据

每个 run 范围内的评论都以隐藏的 run marker
`<!-- orbi:run=<run_id> -->` 开头。marker 携带 run 身份，但不认证作者，
因此消费者仍使用自己的可信作者规则。四种类型是官方元数据，写在 run
marker 之后的下一行：

```html
<!-- orbi:run=86b57234 -->
<!-- orbi:comment=review-round -->
```

- `started`：`Orbi started Pi:` 评论。
- `failure`：完整的诊断/行动失败评论（`orbi:failure:v1` 记录及其面向
  读者的 Action 与 Reason）。它既不是实时进度回显，也不是简短的 milestone
  通知。
- `review-round`：已完成的评审报告；其 `orbi:scene:v1` 块提供轮次计数与
  PR URL。
- `merged`：合并回执。

官方元数据占据以 run marker 开头的连续前缀。四条带类型的评论中，类型紧跟
run marker；进度评论保持原有的 run marker 后接进度块的前缀，不带类型；已有的
scene 与 failure 块按适用情况随后出现。引用在正文、原始日志或代码围栏中的
marker 形状文本不是官方元数据：评论由该前缀识别，永不依据被翻译的标题，
且不受支持或格式错误的类型不会被其旁边的文字重新解释。存在但无效的结构化
块不会被其旁边的文字静默替代。在进度块之前写入的进度评论，以及没有类型标记
的历史英文评论，保留既有的英文标题回退。

只有带有效 scene 的 `review-round` 评论才是新的轮次记录；复用上一 scene 的
评审失败是 `failure`，不消耗轮次。评论类型不增加任何任务状态或恢复记录：
GitHub Issue 与标签仍是唯一状态存储。

### 合并回执

合并回执是一条评论，其唯一的 details 元素携带完整的固定机器行
`merge_commit`、`review_rounds`、`commits`、`external_commits`、
`run_id` 与 `pr_url`，每行恰好出现一次。`pr_url` 是明确的 PR URL，因此
消费者不从摘要标签中提取 PR——摘要标签是展示文本，可以被翻译。缺失、重复或
冲突的行或块会被拒绝，别处引用的行不构成回执，且 URL 必须属于预期仓库。

### 失败诊断

完整失败评论及其简短通知是既有的公开接口：隐藏的
`<!-- orbi:failure:v1 {json} -->` 块（版本、枚举与含义不变）、
`<!-- orbi:fail=<fingerprint>[:count] -->` 去重标记，以及面向读者的
**Action**、**Reason** 与 `Diagnosis` 详情。失败记录的定义见
[Workflow](/zh/workflow)。

`base_ci_red` 失败评论在该记录旁再携带一个隐藏块 ——
`<!-- orbi:base-ci-red:v1 {json} -->`，含 `schema`、`state`、
`base_branch`、`base_sha`、`pr` 与 `failing_checks`。自动恢复就是
原地编辑这条记录（`waiting` -> `resuming`/`stale` -> `merged`）；
稳定性规则相同：一条评论只有一个该块，存在但无效的块绝不会被当作“没有
块”，旁边的可读文字仅供展示。

## 澄清提案与命令回执

工单评论上有两处机器可读的公开接口：澄清停止评论可能携带的提案，以及票内命令留下的回执。两者都从固定标记读取，绝不依赖旁边可被翻译的文字。

### 澄清提案区块

当 Orbi 的澄清门禁（认领时对可观察结果、验收条件与单一结果的检查）停下一张正文已经足以给出修复方案的工单时，停止评论会在两个固定标记之间携带这份提案。只有两种情况会渲染：

- 仅缺少 `single_outcome`：`kind=split`，每个新工单一个编号条目，各带自己的验收行，并可选依赖更早的条目；
- 仅缺少 `acceptance_condition`：`kind=criteria`，每个验收条件一行。

其他所有停止评论——缺少别的要素、缺少第二个要素、工单缺少提案所需的事实，或修复需要只有人才能做的决定——保持原样，不带任何区块。

```html
<!-- orbi:suggestion:v1 kind=split -->
1. Users can tag a note
   Acceptance: after adding a tag, filtering by it finds the note; the tag survives a reload
2. Users can export a note as Markdown (after 1)
   Acceptance: Export downloads a .md file with title, body and tags
<!-- /orbi/suggestion -->
```

```html
<!-- orbi:suggestion:v1 kind=criteria -->
- Adding a tag makes the note findable by filtering
- The tag survives a reload
<!-- /orbi/suggestion -->
```

渲染出的区块之后会跟一句显示文字——英文 `Editing this comment changes the proposal.`，中文 `编辑这条评论即可修改这份提案。`——除上述含义外不承载任何语义。每种提案还会多一句显示文本，点名处理它的命令：
`kind=split` 段落为英文 *Reply `/orbi split` to create these tickets.*，
中文 *回复 `/orbi split` 即可创建这些工单。*；
`kind=criteria` 段落为英文 *Reply `/orbi add-criteria` to add these and
start.*，中文 *回复 `/orbi add-criteria` 即可把这些加入工单并开始交付。*

条目编号、`(after N)` 短语（中文为 `（等第 N 条）`）与 `Acceptance:` 前缀（中文为 `验收：`）来自消息目录，因此中文工单渲染中文行语法，而解析器接受所有目录语言。

### 行语法与解析

标记之间每一行都是下列之一：

- 起始标记 `<!-- orbi:suggestion:v1 kind=split -->` 或
  `<!-- orbi:suggestion:v1 kind=criteria -->`；
- `kind=split` 的条目行 `<n>. <result>`，紧接验收行
  `   Acceptance: <text>`，结果后可带 ` (after <n>)`；
- `kind=criteria` 的条目行 `- <condition>`；
- 结束标记 `<!-- /orbi/suggestion -->`。

区块内的空行会被忽略。条目编号必须唯一，`(after N)` 必须指向区块中更早写出的条目：因此可以删除、改名与重排行，只需保持这一条规则。

一个解析器读取整条评论正文，返回解析出的条目，或第一条无效行的行号（从 1 起算，包含标记与文字）：

- 没有起始标记：没有提案，这不是错误（与这份契约之前的停止评论同一结果）；
- 未知的 `kind` 或缺少结束标记：起始标记所在行；
- 结束标记之前出现第二个起始标记：该行；
- 空区块：结束标记所在行；
- 既不是上述形状的行、重复的条目编号、下一行不是自己验收行的条目（报告该条目行）、`(after N)` 指向自己、之后的条目或不存在条目：该行。

```text
missing end marker: the body ends before the end marker, so the start marker's line is reported
empty section: the start marker immediately followed by the end marker
duplicate item numbers: two items carrying the same number
item without acceptance: an item line followed by anything but its acceptance line
item line without a number: Users can export a note
acceptance line without its prefix: Receipt: filtering by the tag finds the note
after itself: 2. Export a note (after 2)
after a later item: 1. Tag a note (after 2), written above item 2
after a missing item: 2. Export a note (after 7), with no item 7 above it
unknown kind: kind=plan
criteria item is not a condition: 1. Tag a note inside a kind=criteria section
second start marker: a start marker appearing before the end marker
```

### 权威停止评论

权威停止评论是 Issue 上最新一条同时满足两点：带有正式停止前缀——可选的 `@author` 提及行、run marker 以及隐藏的 `<!-- orbi:clarify-stop:<digest> -->` 标记——且由本 Runner 撰写（与停止标记本身相同的信任规则）。选择依据是评论创建顺序，绝不是编辑时间，因此编辑一条停止评论不会改变它的位置。最新的受信停止评论就是权威，即使它没有携带提案：绝不沿用更早停止评论里的提案，别人写的更新评论也不会被选中。

### 把提案变成子工单

`/orbi split`（票内评论，或 `orbi split --repo <owner/name> --issue <N>`）读取
它所运行工单最新一条可信停止评论，按本页描述的语法解析段落，为每个
`kind=split` 条目创建一张子工单 —— 按运行那一刻评论的内容，所以先编辑评论
就会改变创建结果。只有 `kind=split` 段落是合法输入：`kind=criteria` 提案、
缺少段落或某一行无效都会被拒绝，回执写明原因（行无效时还写明行号）。

子工单是一张普通工单，它的正文同样是公开契约：

```text
## Outcome
<条目的结果>

## Acceptance
- <条目的验收行>

Split from #<父工单号>

<details><summary>Parent ticket text</summary>

<父工单的正文>

</details>

<!-- orbi:split-child:<父工单号>:<条目号> -->
```

该标记让重跑找到已经创建的子工单；只有当工单由本 Runner 创建 —— GitHub 在
工单上把该账号报告为 `app/<name>`、在评论里报告为 `<name>`，因此比较的是账号
而不是载荷形状 —— 且标题、验收行与原生 `after` 依赖仍与条目一致时才算数：
伪造或复制的标记、被编辑过的条目、或两张同时匹配的工单都会让命令停下并发一条列出已有内容的回执 ——
绝不盲目复用。子工单会挂成父工单的原生子工单，`(after N)` 记为原生
`blockedBy` 关系，只继承父工单的 `p0`（若有）、`bug`（若有）与里程碑，
并得到派发标签。父工单随后标记 `ai-epic` 并摘掉派发标签，`ai-needs-detail`
在最后、在列出子工单的那条回执之后才移除 —— 因此中断的运行会被下一个 tick
接着做完。

### 追加提案中的验收条件

`/orbi add-criteria`（票内评论，或 `orbi add-criteria --repo
<owner/name> --issue <N>`）读取该工单最新一条可信停止评论，按本页规则解析
其中的段落，并把每条 `kind=criteria` 条件 —— 按评论当时的内容 —— 追加
到工单正文 `## Acceptance` 标题下，其后跟隐藏标记
`<!-- orbi:acceptance:v1 -->`：

```text
## Acceptance
- <第一条条件>
- <第二条条件>

<!-- orbi:acceptance:v1 -->
```

该标记让追加保持幂等：某一步失败后的重跑会读到它而不再追加，因此正文只会
得到一次该段落。只有 `kind=criteria` 段落是合法输入：`kind=split` 提案、
没有段落或某一行无效都会被拒绝，回执写明原因（行无效时还给出行号），且
什么都不会写入。随后工单得到派发标签与一条列出这些条件的回执，并在最后
才移除 `ai-needs-detail`。

### 命令回执

票内命令（`/orbi milestone <version>`、`/orbi fix-base`、`/orbi split`、`/orbi add-criteria`）对每种结果各留一条回执评论。回执的隐藏标记同时标明命令与结果，其 `comment=` 键标明它所回答的命令评论：

- `<!-- orbi-<name>-command comment=<key> -->`：命令已执行；
- `<!-- orbi-<name>-command-rejected comment=<key> -->`：未被采纳（权限、参数形状或命令自身的规则）；
- `<!-- orbi-<name>-command-failed step=<step> comment=<key> -->`：已进入处理函数并在该步骤失败。

`<name>` 是命令稳定的机器 id（`fix_base`、`milestone`、`split`、`add_criteria`），不是人输入的词，因此 `/orbi` 前缀之前发出的回执仍然匹配。`<key>` 是被回答评论的 GitHub id，其次是它的 URL，都读不到时是 `<login>@<createdAt>`——与 `/orbi fix-base` 成功回执已经使用的键相同。标记周围的文字是工单语言的显示文本，因此消费方从标记前缀与 `step` 字段判定结果，通过 `comment=` 定位命令评论，绝不解析被翻译过的句子。

```text
<!-- orbi-fix_base-command comment=3456789012 -->
<!-- orbi-fix_base-command-rejected comment=3456789013 -->
<!-- orbi-fix_base-command-failed step=look up the triage Issue comment=3456789014 -->
```

## 工作示例

### 并发 Issue

两个已配置交付同时运行。每个 Issue 都显示自己的归属观察，因为观察键包含仓库与 Issue 号；本地周期保留每个并发活跃交付，而不是一个当前 run。

### 保留的 session

交付 A 已完成，它的 Issue 离开最近一次成功 GitHub 范围读取，但 worktree 与 JSONL 仍在磁盘上。A 会从活动行移除：保留的 session 是历史，不是当前执行。如果 A 的实际 GitHub 状态再次变化、新的范围读取又包含它，它可以再次出现。

### 尚无摘要的新 run

存在新的 run 记录——有 run 标记、没有 progress block。它的摘要归为 `missing`：展示该 run 自己的字段，不用另一个 run 的摘要当作它的报告。

### 不支持的或损坏的报告

progress block 带未知版本或畸形 JSON。摘要归为 `unsupported` 或 `invalid`；视图其余部分照常展示，命令不崩溃。

### 终态或手动状态优先

Issue 已关闭或已合并，或正在等待已确认的手动动作。该 GitHub 事实优先于本地观察展示，本地记录绝不用于声称交付仍在运行。

## 本页不承诺什么

- 不是第二个状态存储：GitHub Issue 与 label 仍是唯一状态。
- 不是端到端时延保证：记录级观察不是 token 流。
- 不是机密扫描器：路径策略过滤已知边界，而不是任意文件。
