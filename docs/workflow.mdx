# Workflow

Orbi claims an eligible Issue, implements it in a worktree, opens a PR, independently reviews it, merges it, and records the result.

One Orbi task is one runtime outcome, in one of two shapes:

- **Fix** — when X, should Y, actually Z. Example:
  [#1074](https://github.com/orbi-build/orbi/issues/1074) — when
  `gh auth status` exits 1 while the active account is valid, the
  Runner should resolve it; actually the exit code failed the delivery.
- **Change** — when X, the user should be able to Y; today they
  cannot because Z. Example: [#1048](https://github.com/orbi-build/orbi/issues/1048) —
  when a user starts the runner from the published image, they should
  get a working model provider; nothing read the `ORBI_PI_*` variables yet.

A task starts as a GitHub Issue and ends as a merged PR (or an
`ai-blocked` scene that needs a human). This page covers the complete
automatic chain and the project's GitHub workflow vocabulary.

## The complete chain

State machine (the six delivery states; the review/fix loop stays on the
same PR — only its head may advance):

```mermaid
flowchart LR
  epic["Epic (ai-epic) — coordination only, never claimed"]
  epic -.splits into.-> ready
  release["Release task (ai-ready + ai-release)<br/>— Runner release state machine, never run_pi"]
  release -.claims like.-> ready
  ready["ai-ready<br/>(pickup order: P0-labeled first, then bug-labeled, then plain)"]
  ready -->|claim: label + worktree + Pi| progress["ai-in-progress"]
  progress -->|PR verified: base fresh, run marker, Fixes #N| opened["ai-pr-opened"]
  opened -->|independent review session, fixes in-session| verdict{REVIEW_VERDICT}
  verdict -->|clean verdict + merge gate| merged["ai-merged (terminal)"]
  verdict -->|rounds exhausted (human decision)| blocked["ai-blocked (terminal, human decides)"]
  opened -->|finding / base conflict / recoverable failure (Issue #50)| fixneeded["ai-fix-needed"]
  fixneeded -->|next tick: next review session on the SAME run, branch, worktree, PR| opened
  fixneeded -->|unrecoverable precondition (Issue #50)| blocked
  progress -->|fail fast (no PR yet)| blocked
```

```text
ai-ready                a task is dispatched (orbi add, or a human
                        adds the label)
  -> ai-in-progress     the Runner claims it: label added, worktree created
                        from the frozen origin/<base> SHA, Pi session starts
                        (the prompt carries the Issue body plus the
                        trusted-comment timeline {{ISSUE_COMMENTS}},
                        Issue #745: OWNER/MAINTAINER/MEMBER/COLLABORATOR
                        comments only, capped by issue_comments_limit with
                        a visible omission note)
  -> ai-pr-opened       the PR passes verification (base freshness, run
                        marker, Fixes #N); the tick then ENDS and
                        releases the slot (Issue #788) — the delivery
                        awaits its review tick
  -> review             one tick, one step: the resumable scan
                        classifies the opened-PR delivery RESUME_REVIEW;
                        if the PR head's CI is still pending the tick
                        journals it and returns (no sleep); otherwise an
                        independent Pi session — the ONLY blocking phase,
                        so the slot is held for exactly the Pi run —
                        reviews the exact base/head SHAs and FIXES
                        findings in-session (code, full test suite,
                        tiered coverage gate (Issue #234), push only the
                        task branch), then emits a REVIEW_VERDICT. Its
                        prompt carries the linked Issue's trusted timeline
                        and trusted human feedback on the CURRENT PR:
                        formal review state plus inline file/line anchors.
                        The runner identity is excluded; PR feedback is
                        input only, never delivery state or PR labels.
                        Reads are bounded and a GitHub read failure is
                        logged and falls back to Issue comments.
  -> ai-fix-needed      a finding could not be fixed in-session, the PR is
                        behind the latest base / has a merge conflict, or
                        an AI-recoverable failure of the existing run/PR
                        (Issue #50: a Pi execution failure, a verification
                        failure, an unpushed local commit): the failure
                        comment is written to the Issue AND the PR with
                        the full scene (run_id, PR, branch, worktree,
                        session, phase, last activity, concrete error),
                        and the NEXT tick starts the next review session
                        on the same run_id, branch, worktree and PR
  -> merge              clean verdict (its head field equals the PR
                        head, Issue #591) + merge gate (head contains
                        the latest base, CI concluded, PR mergeable,
                        remote head unchanged — each read ONCE: pending
                        CI or an UNKNOWN mergeability defers the merge
                        to the next tick, Issue #788)
  -> ai-merged          Orbi merge mode: success terminal state; the PR
                        body's Fixes #N closes the Issue natively
  -> ai-awaiting-merge  known policy blocker: the Issue comment names the
                        one maintainer action; Orbi resumes and merges after it
```

A failure of an existing run/PR is classified (Issue #50): an
AI-recoverable failure (a Pi execution failure, a verification failure, an
unpushed local commit, a finding that could not be
fixed) keeps the Issue in the automatic fix loop — `ai-fix-needed` with
the failure comment on the Issue AND the PR carrying the full scene — and
the next tick resumes the same run, branch, worktree and PR (no
replacement PR, no re-claim). A missing worktree is not a failure at
all: the resume rebuilds it from the remote delivery branch and
continues (Issue #807 — the worktree is a local cache of the remote
state, branch + PR live on GitHub). Only an external precondition the AI cannot
safely judge or fix (an unrecoverable scene, a base-branch config change,
an exhausted review round budget, a PR closed without merge, a delivery
branch deleted from the remote — nothing left to rebuild the worktree
from) fails fast:
the Issue is marked `ai-blocked` with the explicit reason why automatic
recovery is impossible, and the automatic loop never touches it again — a
human decides the next step.

## Steering an active delivery

You can correct direction without cancelling an active delivery. While the
Issue is `ai-in-progress`, add a comment with the new decision or edit the
Issue body. These two channels are equivalent: both are picked up by the
Runner's next steering poll (the interval is `steering_poll_seconds`, 60
seconds by default), and the active session restarts with the correction. The
restarts are bounded by `steering_max_rounds` (3 by default); after the limit
is reached, further corrections do not restart that delivery and the journal
records `steering_limit_reached`. Let the current delivery finish, then put the
revised scope in a follow-up delivery.

Only comments from trusted repository roles—OWNER, MAINTAINER, MEMBER, or
COLLABORATOR—can steer a run. A comment from a public commenter is ignored by
design, because allowing arbitrary commenters to steer a delivery would expose
a prompt-injection path. The initial trusted comment timeline is capped at
`issue_comments_limit` (20 by default): older comments are dropped and the
injected context states how many were omitted.

Dead-loop guard and comment dedup (Issue #825): a resume may bind a NEW
run id (one recoverable failure is enough), while the PR body is written
once at creation, so the resume verification accepts ANY run marker the
delivery line has used — the marker set is read from the Issue's TRUSTED
comments (the same trust filter as the resume scene; a copied marker in a
public comment widens nothing, and the branch, base, head and exact-URL
checks stay intact, keeping the #45/#89 anti-PR-swap posture). A failure
comment of one `(run_id, failure fingerprint)` pair is posted ONCE (the
hidden `<!-- orbi:fail=... -->` marker is the key); every identical
repeat bumps that comment's hidden `:<count>` suffix in place (the
journal records the repeat). The same pair recurring to 3 CONSECUTIVE
failures (a scene block — a newly opened PR, a completed review round —
means the line advanced and resets the streak) is classified as a dead
loop, not a transient error: it escalates to `ai-blocked` with the count
and the unchanged-precondition verdict in the comment.

Rules of the chain:

- One task = one run = one feature branch = one worktree = one PR. The PR
  number never changes during the review/fix loop; only its head may
  advance.
- Only the two opened-PR states are picked up automatically:
  `ai-pr-opened` (awaiting review) and `ai-fix-needed` (awaiting the next
  review session). `ai-ready` is claimed as new work; `ai-blocked` is
  never auto-recovered. A delivery that carries the backfilled
  `ai-in-progress` label is still picked up (Issue #178: a runner killed
  during review leaves it behind — the positive opened-PR qualifier
  already keeps implement-phase Issues out of the scan).
- The review/fix loop is bounded (5 rounds). The completed-round count
  lives in the trusted scene (`review_round`, Issue #788): every round
  comment carries the updated scene block, so the next tick reads the
  advanced count from it (a human's blocked -> ai-fix-needed recovery
  after the scene still starts a fresh budget, Issue #483). Exhausting
  rounds with findings marks the Issue `ai-blocked` (the bounded loop is
  a human decision); a recoverable failure (Issue #50) keeps it
  `ai-fix-needed`. Either way the PR, branch and worktree stay intact.
  The reviewer guards the budget itself (Issue #878): before the work
  its prompt reads the delivery's round comments (the same `run_id`) and,
  when the same failure reason already appears in two or more consecutive
  rounds, emits the findings verdict naming the repetition instead of
  repeating the fix — a wall is hit by at most two rounds.
- No in-tick waiting (Issue #788): the old in-process wait loop
  (`wait_for_delivery`, CI/mergeability polling with
  `release_ci_wait_seconds` / `mergeable_wait_seconds`) is gone. Every
  wait is the waiting primitive — write the state, return, release the
  slot, and the next tick re-reads (`delivery_ci_pending`,
  `merge_gate_ci_pending`, `merge_gate_mergeable_unknown`). The
  crash-recovery path IS the path.
- Base advances are absorbed by a plain `git merge` of the latest
  `origin/<base>` on the task branch (conflicts resolved manually),
  followed by a full test rerun. No force push, no auto conflict
  resolution, no push of the protected branch.
- Absorb contract (Issue #877, machine-checked by the Runner): a review
  round that starts with the head behind `origin/<base>` or facing a
  merge conflict must end in one of two states — the branch contains
  `origin/<base>` (`git merge-base --is-ancestor` true), or the verdict
  is `findings` stating that the round attempted the absorb and
  abandoned it, with the concrete reason. A `pass` whose head still
  lacks the base is named in the round comment as an absorb-contract
  violation (`review_absorb_abandoned`); the bounded 5-round semantics
  are unchanged.
- Git transport (Issue #114, #580): git data operations go over the
  configured transport (`git_transport`: `ssh` by default — git over
  SSH —, or `https` with
  the `gh` credential helper), GitHub
  API operations stay on the `gh` token — the full two-channel boundary
  and the pre-start check: [Operations](/operations); the credentials:
  [Security](/security).

### Reviewing with a different model

The independent review does not have to run on the model that wrote the
code: `review_pi_provider`, `review_pi_model` and `review_pi_thinking`
select a separate provider/model/thinking level for the review session,
so the reviewer does not inherit the author's blind spots. Each key
falls back independently to its implementation-side value
(`review_pi_provider` → `pi_provider`, `review_pi_model` → `pi_model`,
`review_pi_thinking` → `pi_thinking`), so overriding only one of them is
valid. Both selections must exist in the configured `pi_providers`
catalog and are validated separately at startup — an invalid review
selection fails fast with `review provider selection invalid`. No
specific pairing is recommended or benchmarked here; the capability and
the fallback are the contract.

```toml
# The implementation runs on one model, the independent review on another.
pi_provider = "z-ai"
pi_model = "glm-5.3-flash"

review_pi_provider = "groq"
review_pi_model = "groq/compound"
```

## The merge record: `external_commits` and `commits`

When the Runner merges a delivery PR, the `Orbi merged PR:` Issue
comment and the `Orbi: merged` milestone line carry the merged-as-is
fact (Issue #833) in the same `key=value` format as the other fields:

```
Orbi merged PR: <url> (merge_commit=… review_rounds=N external_commits=K commits=M base_branch=… run_id=…)
```

- `commits` — all commits of the PR branch relative to the base at
  merge time (the denominator of the ratio).
- `external_commits` — commits NOT in the engine's own push history
  (the head the PR opened with plus every review/fix head the Runner
  itself pushed; git authorship is never inspected). `0` = merged
  as-is: no human changed a line on the delivery branch before the
  merge. The count is read after the merge through the merge commit's
  parent chain (`M^1` the base tip, `M^2` the PR head) minus the
  engine's recorded push line: the last engine-pushed head, and — for
  an external takeover (Issue #608) — excluding the taken-over
  contributor head the line starts from, so the contributor's commits
  stay external.
- `external_commits=unknown` — the push history is unverifiable (a
  recreated worktree lost the run-state record, a fix push's round
  ended before its record and the history is incomplete, or a recorded
  head or base is not an ancestor of the merged head). An uncountable
  history is never written as `0`.

The engine's pushed heads are recorded in the task worktree's run state
(`pushed_head`, Issue #219 file) at three points — the delivery push,
a verdict-covered review/fix push, and the round-start adoption of a
head a previous session pushed but whose round ended before the
re-freeze record — so resumes of the same worktree keep the history; a
fresh worktree starts without it and degrades to `unknown`. An
external takeover additionally records the taken-over head once at
claim time (`pushed_base`), and its round-start adoption never runs:
the worktree legitimately starts on the contributor's head. Recording
is bypass-safe: a missing or corrupt state file logs
`pushed_head_unrecorded` and the delivery continues.

## Delivery labels

GitHub labels are the external state machine. They are not created by
commits — initialize them per repository (see
[Getting started](/getting-started)):

| Label | Meaning |
|---|---|
| `ai-ready` | Explicitly dispatched to Orbi; may be claimed |
| `ai-in-progress` | Claimed and running. The Runner idempotently backfills it before continuing a resumed opened-PR delivery (Issue #178); a leftover after a kill is resumed by the next tick |
| `ai-pr-opened` | PR created and verified; awaiting the independent review |
| `ai-fix-needed` | The PR head is not mergeable yet, or an AI-recoverable failure of the run/PR (Issue #50); the next tick resumes the same run, branch, worktree and PR |
| `ai-merged` | Success terminal state; the Runner merged the PR and confirmed the merge commit on the protected branch |
| `ai-awaiting-merge` | Review and checks passed, but a known repository policy blocker remains; the comment names the maintainer action and Orbi resumes to merge the named PR head |
| `ai-blocked` | Only an external precondition the AI cannot safely judge or fix (Issue #50); the blocked comment states why automatic recovery is impossible; a human must decide the next step |
| `ai-human-review` | The human acceptance gate (Issue #763): a person confirmed the delivery's acceptance checklist. Only a human applies or removes it — the Runner never touches it |

A repository policy may block the merge even after Orbi's review and checks
pass. Orbi stops at `ai-awaiting-merge`; the Issue comment names the exact head
and the one maintainer action (including the settings URL when applicable).
After the maintainer changes the policy or supplies the required approval, a
later tick resumes and Orbi merges the PR itself. A policy rejection without a
known FAILED preflight action, or any other merge failure, remains
`ai-blocked`.

## Human acceptance gate (ai-human-review)

The main line of the product is unattended: the default pipeline runs
with humans OUT of the loop, and the gate is off by default — with the
switch off the delivery, review, merge and release behavior is exactly
what it was before (Issue #763).

The host config turns the gate on (`human_review_gate = true` in
`orbi.toml` — an operator trust decision, not a repository policy).
Every delivery then posts ONE acceptance checklist comment to the Issue
when its PR opens, split in two columns:

- **Column 1 — what the run already verified** (evidence, not todos):
  the real test result from `.orbi/test.log`, the covered layer (the
  repository test suite), the delivered file count.
- **Column 2 — the machine-unverifiable minimum**, derived per
  delivery from the changed paths and the available evidence (never a
  hardcoded human-items template): business intent (tests prove the
  implementation matches the tests, not that the tests match the
  intent), UI visuals and copy, external-environment verification, and
  missing-evidence items when the test log or the diff cannot be read.

While column 2 is non-empty, it is a GATE: the review round
short-circuits before any Pi session — the ticket returns to
`ai-ready` (the opened-PR label stays as the resume anchor), the slot
is released, and every later tick costs one label read. The wait does
NOT consume the review-round budget and never touches
`ai-fix-needed`. A person who confirms the checklist applies
`ai-human-review`, and the next tick reviews and merges the delivery
exactly as it does today (the verdict binding and
`--match-head-commit` are untouched).

An EMPTY column 2 is the target state: the checklist says
无需人工介入 ("no human intervention needed") explicitly and the
delivery passes without the label. As model capability grows,
column-2 items migrate into column 1 — the checklist comment carries a
machine-parsable `<!-- orbi:human-review {...} -->` block (schema 1)
so the migration is toolable without changing the artifact shape. The
checklist makes no correctness guarantee of any kind: column 1 is
evidence of what was verified, column 2 is what a person still
confirms.

## Ticket dispatch: content, dev and ops

`ai-ready` is the execution switch for every task type; a second label
selects the type (Issue #537). Three types exist — pick one per Issue at
dispatch time:

| Ticket type | Labels | What the Runner does |
|---|---|---|
| dev (the default) | `ai-ready` | The full delivery chain: worktree, dev playbook, one PR, independent review, merge |
| ops | `ai-ready` + `ai-ops-only` | The SAME full execution session (worktree, shell, network — no command whitelist exists anywhere in the implementation), but the ops playbook replaces the dev one. The deliverable is the evidence posted on the Issue; when the session commits code, the delivery takes the normal PR ceremony |
| content | `ai-ready` + `ai-content-only` | The content agent: text in, text out, delivered as an Issue comment — no execution, no git; the Issue is closed after the delivery |

Ops semantics (Issue #537):

- **The trust boundary is (credentials, ticket) — never a command
  whitelist.** The session receives the runner's whole environment
  unfiltered (gh auth, `CLOUDFLARE_API_TOKEN`, AWS keys, ... plus the
  deploy-home `.orbi/env` file); how wide the credentials are is the
  user's decision — the runner never trims them.
- **The ticket body is the authorization.** The session executes only
  the ops actions the ticket states (which PR to merge, which
  environment to deploy); an action beyond the ticket is reported in a
  comment and the session stops. Human approval gates (environment
  approval, Release approval) are never performed by the session — a
  prompt convention, not enforced code.
- **Delivery = evidence** (the fact culture of Issue #526): every step
  posts the real command and its real output / API response verbatim on
  the ticket; a step not executed is labeled as not executed. A
  pure-ops run (no commit) ends with the Runner closing the Issue and
  removing `ai-in-progress` — no PR. Committed code takes the normal PR
  path with review and merge.

Research-only tickets (Issue #739): a ticket whose body demands
investigation only — "research/design first, do NOT implement yet" —
is an ops ticket at dispatch time: give it `ai-ready` +
`ai-ops-only`. A dev ticket cannot carry that instruction: the dev
delivery criterion is a commit on the task branch, so an agent that
correctly follows it delivers no commit and the run fails with
`the agent delivered no commit` — the Issue is burned `ai-blocked`.
The ops playbook's evidence discipline (real commands, verbatim
output, unverified items labeled as such) IS the research
deliverable; a no-commit ops run completes normally (the Issue is
closed, `ai-in-progress` removed), and research that continues into
code still takes the normal PR ceremony.

Before Issue #537 the label `ai-ops-only` dispatched the content agent
(the #530 rename never changed the behavior — the name promised ops,
the mode was content-only); the content path dispatches on
`ai-content-only` now, and `ai-ops-only` is the full-execution ops
path.

## Run marker and run_id

Every task attempt generates one `run_id` (8 hex chars, e.g.
`e07383c2`) and reuses it for every step of the attempt; a retry of the
same Issue generates a new one. The same id appears in:

- every journal line of the attempt (prefix `[e07383c2]`);
- the Issue/PR comments: visible field `run_id=e07383c2` plus the hidden
  machine-readable marker `<!-- orbi:run=e07383c2 -->`;
- milestone and scene comments also carry the hidden runner marker
  `<!-- runner=1a2b3c4d -->`: a fingerprint of the deployment that wrote
  them — the executing checkout's HEAD, the package version for a
  non-editable install, or `unknown` when the probe fails (the live
  progress comment and PR comments do not carry it);
- the `Orbi opened PR` scene comment carries the hidden versioned run
  scene `<!-- orbi:scene:v1 {json} -->` (`src/orbi/scene.py`): the
  machine-readable recovery record the resume scan parses — a corrupted
  scene and a missing scene are distinct failure branches (Issue #786);
- the stable Issue-based feature branch (`orbi/<owner>-<repo>-issue-<N>`);
- the worktree name (`.worktrees/orbi-<owner>-<repo>-issue-<n>-e07383c2`), plus
  the Pi session directory and run artifacts;
- the PR body — the stable marker `<!-- orbi:run=e07383c2 -->` is
  part of the PR contract; the Runner rejects a PR without it.

Reconstruct a full timeline with one grep:

```bash
journalctl --user -u orbi@1.service -u orbi@2.service | grep e07383c2
gh search issues "e07383c2" --repo OWNER/PILOT-REPO
```

## PR body contract: `Fixes #N`

The PR description must contain `Fixes #<issue-number>` (it may be on the
first line). GitHub reads the body (not the PR title) and closes the Issue
natively when the PR merges into the default branch. The Runner verifies
the keyword during PR acceptance and fails fast when it is missing.

## Epics, Release tasks and P0 priority

The project organizes multi-task work with plain GitHub primitives — no
DAG, no priority numbers, no separate queues:

- **Epic**: a coordination Issue that groups a set of related tasks (for
  example the v0.1 release checklist). It is marked with the `ai-epic`
  label. An Epic is not itself a directly executable task: the actual
  work is split into independent `ai-ready` Issues, each with one runtime
  outcome, one PR, one review and one merge. The Runner NEVER claims an
  Epic (Issue #93): the ready claim scan skips it with the structured
  `epic_not_claimed issue=N repo=...` journal line (no claim, no label
  change, no worktree, no run, no slot), and the restart-resume scan
  excludes it too. Epic completion is declared exclusively by GitHub's native
  `sub-issues` relationship: every child Issue must be closed (or its PR is
  merged) and there must be no open native `blockedBy` dependency. References
  in the Epic body, including `Children`/`Child Issues` sections, are not
  declarations. An Epic with no native sub-issues, or malformed child or
  dependency state, fails closed. The Runner reconciles open Epics on every
  tick and leaves an idempotent audit comment. Any prose describing extra
  acceptance conditions is an Epic definition error: make that condition a
  final child Issue instead (for example, a browser acceptance ticket). The
  same tick then reconciles open Milestones: an exact-title published Release
  (draft excluded) plus zero open Issues closes the Milestone; all other cases
  remain open. The same tick finally sweeps open PRs (Issue #746): a
  stable-delivery PR (`orbi/<repo>-issue-<N>` head branch) whose source Issue
  a human closed is reported ONCE on the PR with an idempotent comment —
  every resumable scan reads `state=open` Issues only, so without this sweep
  the PR would dangle forever. The merge/close decision stays with the
  human: the Runner never auto-merges and never auto-closes across a human's
  close.
- **Release task**: an `ai-ready` Issue additionally marked with the
  `ai-release` label (Issue #98). It is NOT a development task: the
  Runner picks it up through the normal ready scan, but `process_issue`
  routes it to the deterministic release state machine instead of
  `run_pi` — no Pi session, no PR. The state machine is idempotent and
  resumable (a restart resumes the same run id/worktree) and runs these
  steps in order:

  1. Strictly parse the `## Release` declaration from the Issue body:
     `version`, `base_branch`, and `scope` (a list of `#N` items) or
     `scope_from_milestone`, plus optional `version_file`
     (`pyproject.toml` by default, `package.json`, or `none`). The
     declaration carries NO test contract (Issue #569): test
     acceptance is the GitHub Actions CI result on the release commit
     (the Issue #268 CI-wait gate). Missing, duplicated or unknown
     fields fail fast.
  2. Freeze the base — the release commit is exactly
     `origin/<base_branch>` (fetched under the base-sync lock). Before
     any gate wait, the declared (or defaulted) `version_file` is
     proven to exist at the root of that frozen tree (Issue #740): a
     mismatch fails fast at claim time, naming the supported ecosystem
     files that DO exist there and the `none` option, never as a late
     FileNotFoundError after the gates and the scope verification.
  3. Enforce the pre-release gates: no leftover open `ai-in-progress` /
     `ai-pr-opened` / `ai-fix-needed` Issues **in the release's
     Milestone** (Issue #671; the release Issue itself excluded; without
     a Milestone the repository-wide scan is unchanged), and CI green on
     the release commit (no check runs passes
     with explicit evidence; a pending check is an intermediate state —
     the gate waits for the final conclusion, one `release_waiting_ci`
     journal line and one progress-comment update per poll, up to
     `release_ci_wait_seconds` (default 1800 s); a wait timeout fails
     with its own reason, never reported as a CI failure). Open PRs are
     deliberately NOT a gate (Issue #608, maintainer ruling): an open PR
     is queue state, never a release premise — whether open PRs exist,
     how many, or who authored them says nothing about the release; a
     stranded PR is the delivery loop's takeover/reconciliation job. A
     gate that cannot be checked because of a real `gh` failure is a
     failed gate.
  4. Verify the scope item by item: `gh pr view` must report `MERGED`,
     otherwise `gh issue view` must report `CLOSED` with `stateReason`
     `COMPLETED` — a `NOT_PLANNED` closure (duplicate / won't fix) is
     annotated in the Scope evidence as excluded and never enters the
     Changelog, and a Changelog PR link is written only when its PR is
     merged (Issue #707). Checkbox parsing
     is forbidden — every scope item is checked against the live API.
  5. Test acceptance is the CI-wait gate on the release commit: after
     the version bump the gates re-run against that exact commit
     (step 3's `release_ci_wait_seconds` wait), and a red or timed-out
     CI takes the existing recoverable failure path (`ai-blocked`).
     No local test execution (Issue #569) — the release flow is
     bump → push → CI-wait → tag. If Actions is red or times out, the
     existing failure path blocks the release; the version bump may remain
     on `main` as an acceptable state. The bump is idempotent, so repairing
     CI and retrying the release safely prepares the requested version again.
  6. Tag: when the remote tag is absent, create an annotated tag at the
     release commit and push it with a plain push (never `--force`).
     When it exists it must point EXACTLY at the release commit — a
     mismatch fails fast. An existing tag is never moved, overwritten
     or force-pushed.
  7. Publish the GitHub Release (idempotent) whose notes carry the full
     verification evidence: version, tag, release commit, per-item
     scope evidence, gate evidence, test evidence and the run marker.
  8. Sync the docs-site Release notes (Issue #275) — after the GitHub
     Release exists and before the Milestone is closed: generate
     `docs/release-<version>.mdx` and `docs/zh/release-<version>.mdx`
     from the published Release body (no changelog re-implementation —
     #204 owns that), adding the meta the existing release pages share:
     the tag/release-commit mapping, the publish time and the release
     task Issue number; insert the new version at the head of the
     `Releases`/`发布` navigation groups in `docs/docs.json` (both
     languages, latest first); since Issue #1096 both groups nest one
     collapsed `Earlier releases` subgroup — the automated sync inserts
     the new release at the head and moves every entry beyond the three
     newest into that subgroup, keeping the visible group at the three
     newest releases; move the `(latest)`
     title marker from
     the previous latest page to the new one (only the newest page may
     carry it). The file changes are committed to the base branch
     directly (the release path has no PR) and pushed with a plain
     push. Idempotent: an existing page with identical content is
     neither regenerated nor overwritten, and a run with nothing to
     change commits nothing; an existing page with different content
     fails fast. Any failure fails the whole release (`ai-blocked`),
     never a silent skip.
  9. Apply `ai-merged` and close the release Issue (terminal delivery
     transition).
  10. Close the Milestone whose title is EXACTLY the released version
      (Issue #214), then write the success comment (release URL, tag,
      commit, evidence, docs-site Release notes evidence, Milestone
      evidence). Exact title match only (no guessing, no fuzzy match,
      never a different Milestone): close it when it has 0 open Issues;
      already-closed is an idempotent success (no reopen); a missing
      Milestone or remaining open Issues fail fast with the version, the
      Milestone number/url and the open issue list (never a silent skip).
      The release's own ticket is never counted as unfinished work
      (Issue #808): it is being closed by this release, so a stale-open
      listing of exactly that ticket — the issue index lags seconds
      behind the close (Issue #754) — does not block or delay the close,
      while any other open Issue still refuses it.
      Any failure: `ai-blocked` ALONE (a release is a human decision point
      — no automatic retry), the failure comment carries the run marker
      and the concrete reason, and the exception propagates so the tick
      fails fast.

  The `ai-release` label is a type marker, NOT a delivery state: it is
  not part of the delivery-state machine, not an exclusion of the ready
  scan, and the Runner never adds or removes it — only the human does
  (at dispatch time, together with `ai-ready`).
- **P0 priority**: the plain `p0` GitHub label marks an urgent Issue
  (a production outage). It is NOT a delivery state — it only orders the
  ready pickup, never changes the Issue granularity, any delivery state,
  or the terminal-state semantics, and the Runner never adds or removes
  it. The ready pickup order is fixed: `ai-ready`+`p0` →
  `ai-ready`+`bug` → plain `ai-ready` (three `gh issue list` scans
  sharing the exact same exclusions and blockedBy semantics). P0 obeys
  every existing exclusion rule and the single-slot constraint: a
  blocked P0 is skipped (falling back to the bug/plain scans) and an
  in-flight P0 is resumed by the restart scan. A failed P0 run enters
  `ai-blocked` ALONE (the claim label is removed; the `ai-ready`
  residue is excluded by every ready scan), so no tick re-claims it —
  no infinite retry. There is no priority number or weighted queue.

Task dependencies between Issues use GitHub's native `blockedBy`
relation (`gh issue edit N --add-blocked-by M`); the Runner reads the
field and skips Issues with open blockers. `Depends on #N` lines in an
Issue body are not parsed.

## Repository-level delivery policy (`.github/orbi.toml`)

A repository can version its **delivery policy** as code. At claim the
Runner reads `.github/orbi.toml` from the repository's **default branch
tip** through the GitHub contents API — never the task branch, never the
local worktree — and applies its whitelisted keys **per key** over the
host `orbi.toml`. A repository without that file behaves exactly as
before (zero change). The location is fixed; only the file NAME may be
overridden per source repo with the optional `[[repositories]]` entry
field `config_path` (default `.github/orbi.toml`).

Only delivery-policy keys are allowed:

| Key | Type | Meaning |
| --- | --- | --- |
| `base_branch` | string | Delivery base branch for this repository; absent falls back to the matching `[[repositories]].base_branch`, else the host `base_branch`. |
| `active_milestone` | string | The fresh-claim Milestone scope for this repository. The one exception is the external-takeover scan (Issue #842, decision D1): the fifth, last ready scan has NO Milestone qualifier — an external triage ticket (body marker `<!-- orbi:external-pr:N -->`) is claimable regardless, because an external contribution belongs to no version's scope and must never block the release gate. |
| `context_files` | string[] | Repository-relative context files; existence and a size cap are checked before injection. |
| `dispatch_label` | string | The claim label for this repository (default `ai-ready`); the delivery lifecycle labels stay host constants. |
| `steering_enabled` | boolean | Enables trusted correction polling for this repository; absent falls back to the host value. |
| `steering_poll_seconds` | number | Poll interval for this repository; absent falls back to the host value and must be positive and finite. |
| `steering_max_rounds` | integer | Maximum steering restarts for this repository; absent falls back to the host value. |

```toml
# .github/orbi.toml
base_branch = "beta"
active_milestone = "v0.5.0"
context_files = ["AGENTS.md"]
```

Every other key is rejected: an unknown key, a host-only
identity/security key (see [Security](/security)), invalid TOML or a
wrong type fails the claim fast with the offending key names and the
Issue becomes `ai-blocked` — one repository's bad file never affects
another pool. The host-only set also owns host scheduling:
`max_concurrency` can never be delegated to a repository file — the
concurrency slot pool belongs to the deployment host.
`dispatch_label` must not be a delivery lifecycle label
(`ai-in-progress`, `ai-merged`, …): those stay host constants. The block
lands on the Issue the claim selected; a repository whose
`dispatch_label` is not `ai-ready` has no `ai-ready` candidate to block
when the file itself is malformed, so the fail-fast reason is the
journal's `repo_config_invalid` line (no label change, no comment). The
run comment records `repo_config: <sha>`; when the sha differs from the
previous run it also carries the `repo_config_changed` annotation and,
when the previous content is readable, the effective policy diff as
`repo_config_diff`, so a change is always visible on the run. A read
that fails for a transport reason (rate limit, network) is logged as
`repo_config_read_failed` and the host config applies — the degradation
is visible as the missing `repo_config` field on the run comment.
