# Orbi v0.2.0 黑灯软件工厂发布 Thread

> 发布时可将每个 `## N/29` 段落作为一条 X 帖子；Issue 编号和链接保留为证据。

## 1/29

我们发布了 Orbi v0.2.0。

它不是又一个“让 AI 写代码”的工具，而是在建设一座黑灯软件工厂：没有人需要盯着每一步，Issue、Agent、Review、测试、发布和运行验证可以连续运转。

https://github.com/xqliu/orbi

## 2/29 — #48

Runner 停止时，会记录当前正在处理的 Issue。

任务不会因为进程退出就失去上下文；下一次恢复时，知道上一次停在哪里。

https://github.com/xqliu/orbi/issues/48

## 3/29 — #50

AI 可恢复的失败不会直接终止交付。

失败会保留在同一个 PR 和同一个任务现场里，下一轮继续修复，而不是重新开一条重复任务。

https://github.com/xqliu/orbi/issues/50

## 4/29 — #93

Epic 只是协调，不会被 Runner 当成普通开发任务领取。

真正执行的是拆分后的独立 Issue：一个运行时结果，一个 PR，一次独立审查。

https://github.com/xqliu/orbi/issues/93

## 5/29 — #98

Release task 进入了 Runner 的确定性流程。

发布不再靠人工复制命令，而是由系统完成 base 冻结、范围核验、测试、tag 和 GitHub Release。

https://github.com/xqliu/orbi/issues/98

## 6/29 — #105

双 Runner 并发场景增加了回归验证。

即使两个 Runner 同时工作，也不能重复接管正在进行的交付。

https://github.com/xqliu/orbi/issues/105

## 7/29 — #118

KISS/LEAN 被写进开发契约。

每个任务只做满足验收标准的最小完整改动，不为未来猜需求，不添加没有收益的抽象。

https://github.com/xqliu/orbi/issues/118

## 8/29 — #119

Pi 的 provider、model 和 thinking level 可以通过配置指定。

模型选择从隐含的机器状态，变成可复现、可审计的运行配置。

https://github.com/xqliu/orbi/issues/119

## 9/29 — #131

systemd timer 模板变成部署的一部分。

代码合并后，下一次启动会自动同步最新模板，不需要人工反复修复漂移。

https://github.com/xqliu/orbi/issues/131

## 10/29 — #139

可以用 active milestone 限定 Runner 的领取范围。

当前版本的任务不会和其他版本混在一起，发布节奏更清晰。

https://github.com/xqliu/orbi/issues/139

## 11/29 — #140

Muyan Pilot 有了正式的可执行 CLI 入口。

开发入口和部署入口分开，systemd 运行的是明确、可验证的命令。

https://github.com/xqliu/orbi/issues/140

## 12/29 — #142

unit drift 检查增加自动修复和复核。

发现已安装配置和仓库模板不一致时，Runner 会同步、重新校验；仍然不一致才 fail fast。

https://github.com/xqliu/orbi/issues/142

## 13/29 — #149

Runner 使用两个 systemd timer 实例。

调度实例可以并行触发，但实际并发仍由 slot 和 max_concurrency 控制，不会因为 timer 数量失控。

https://github.com/xqliu/orbi/issues/149

## 14/29 — #152

editable uv tool install 成为正式部署方式。

checkout 更新后，下一次 Runner 可以使用最新源码，不再因为旧 CLI 副本卡死启动链路。

https://github.com/xqliu/orbi/issues/152

## 15/29 — #154

文档发布列表按版本倒序展示。

用户打开文档时，先看到最新版本，而不是在历史版本里寻找当前发布内容。

https://github.com/xqliu/orbi/issues/154

## 16/29 — #156

setup 会明确检查 uv 是否存在，并给出可执行的安装提示。

部署失败不再只留下模糊的“命令不存在”。

https://github.com/xqliu/orbi/issues/156

## 17/29 — #157

Pi provider 支持自定义 baseUrl 和外部 OpenAI-compatible 模型。

本地模型、代理和第三方兼容服务都可以接入同一条 Agent 工作流。

https://github.com/xqliu/orbi/issues/157

## 18/29 — #158

pyproject.toml 的 packaging 变化会触发 editable CLI 元数据刷新。

安装环境不会继续使用过期的模块映射，避免合并后 Runner 在启动前就找不到新模块。

https://github.com/xqliu/orbi/issues/158

## 19/29 — #162

Orbi 增加 Prometheus exporter 和 Grafana dashboard。

Runner 的执行状态、slot、Issue、phase 和恢复事件可以被持续观察，而不是只能登录机器看终端。

https://github.com/xqliu/orbi/issues/162

## 20/29 — #169

idle/model_wait 检测不再只看“沉默了多久”。

Runner 会检查上游连接和进程现场，避免把仍在工作的慢模型误杀。

https://github.com/xqliu/orbi/issues/169

## 21/29 — #171

所有更新共享 origin/main 的 fetch 都经过同一把锁。

多个 Runner 不会同时写共享 remote-tracking ref，减少并发 review 中随机失败的现场。

https://github.com/xqliu/orbi/issues/171

## 22/29 — #172

每个运行任务的 Pi provider 配置保持一致。

任务不会因为不同 Runner 或不同 session 获得意外不同的模型配置。

https://github.com/xqliu/orbi/issues/172

## 23/29 — #178

恢复 opened-PR 任务时，会补回 ai-in-progress 状态。

GitHub 上看到的 Issue 状态，和 Runner 实际正在恢复的任务保持一致。

https://github.com/xqliu/orbi/issues/178

## 24/29 — #179

v0.2.0 增加了从依赖安装到端到端运行的完整上手文档。

黑灯软件工厂不仅要能运行，也要能被别人部署和理解。

https://github.com/xqliu/orbi/issues/179

## 25/29 — #181

idle recovery 增加 grace window。

超时命令不会因为一次“刚好超过 deadline”的观察就被误杀，恢复逻辑更接近真实进程行为。

https://github.com/xqliu/orbi/issues/181

## 26/29 — #192

新任务领取可以被限制在 active milestone 内。

版本范围在查询层就被锁定，避免 Runner 误领取其他版本的 Issue。

https://github.com/xqliu/orbi/issues/192

## 27/29 — #198

可观测性也必须可靠运行。

Prometheus exporter 被部署为持久 user systemd service，开机启动、异常自动恢复，监控本身也进入黑灯运行状态。

https://github.com/xqliu/orbi/issues/198

## 28/29 — #201

v0.2.0 的发布门禁也经历了一次真实检验。

并发 E2E 暴露 base 落后的失败现场后，修复保留了 freshness gate：第二个 Runner 可以继续领取下一个任务，但不能接管仍在交付中的 PR。

https://github.com/xqliu/orbi/issues/201

## 29/29 — #197

Orbi v0.2.0 已发布。

Release task 自动完成最终 base 对账、范围核验、测试、annotated tag 和 GitHub Release；发布不是一句“完成了”，而是一份可追溯的交付证据。

https://github.com/xqliu/orbi/issues/197
https://github.com/xqliu/orbi/releases/tag/v0.2.0

这些 Issue 组合起来，就是一座黑灯软件工厂：任务自动进入，Agent 自动实现，Review 自动推进，失败自动留下现场，部署自动校验，运行状态持续可见。
